# AFR по требованию: сеанс по горячей кнопке

Документ для разработчика прошивки slimBOXtv: механизмы запуска AFRd2 внешним приложением,
что уже есть в демоне, что придётся добавить и какие решения нужны с вашей стороны.
**Статус: не реализовано.** Внесено в план после релиза 1.1.0 (до него — только фиксы ошибок).
Разбор по коду — журнал проекта, §84.

---

## 1. Запрос и предлагаемое поведение

Часть пользователей не любит частые смены режима экрана и хочет управлять ими вручную: AFR обычно
выключен, а если плавность не устраивает — человек нажимает назначенную кнопку, AFR включается на
время, гарантированно достаточное для решения, и снова выключается.

Предлагаемый сценарий (сеанс, «burst»):

1. Демон работает в пассивном режиме (`enable=0`): живёт, отвечает на API и статистику, режим не
   трогает и почти не потребляет CPU (один `poll` раз в 300 мс).
2. Внешнее приложение (маппер кнопок, настройки прошивки, shell-скрипт) посылает команду
   `burst <ms>`.
3. Демон входит в обычный активный цикл с дедлайном: измеряет частоту кадров, **один раз**
   переключает режим, при необходимости возвращает режим и уходит обратно в пассив.
4. Возврат — к режиму, который был на момент старта сеанса.

Смысл именно в «одном переключении»: обычный цикл на ролик даёт до трёх-четырёх смен режима
(подъём, замер, сброс потолка, лечение подачи) — это и есть то, что раздражает пользователей.

## 2. Что в AFRd2 уже есть

| Кирпич | Состояние | Где |
|---|---|---|
| `enable=0` → пассивный цикл | **есть**: демон жив, `poll` раз в 300 мс, ни `dumpsys`, ни sysfs, `status` отвечает | `afrd.c:3141`, `trigger.poll.ms` |
| UDP API `127.0.0.1:50505` | **есть**: `help`, `frame_rate_hint`, `refresh_rate`, `color_space`, `status`, `reconf` | `apisock.c:99`, `afrd.h:28` |
| Перезагрузка конфига на лету | **есть**, пассивный цикл её замечает (`atv14_reconf_pending`) | `afrd.c:3151` |
| Возврат исходного режима при остановке | **есть**: `SIGINT`/`SIGTERM` снимают флаг 1035 и возвращают режим | `main.c:425` |
| Сторож приложения и Magisk-модуль | **есть**: heartbeat в shmem, перезапуск после падения | `AFRService.java`, `service.sh` |
| Управление извне «включить/выключить» | **есть**: activity `ru.cobra.afrd.START` / `.STOP` правит `enable` в ini и обновляет mtime — демон подхватывает на лету | `ActionActivity.java`, `Control.reload()` |

Отсутствует ровно одно: команда «включись на N секунд и выключись». Всё остальное — уже в коде.

## 3. Две формы запуска

**A. Резидентный пассивный демон + команда `burst <ms>`** — предлагается как основная.
Демон уже работает; команда лишь переводит его из пассива в сеанс и обратно.

**B. Реальный старт процесса по кнопке** (`afrd --burst 40`, если демона в системе нет).
Процесса нет вовсе, пока не нажали; бинарник сам поднимает демон на время сеанса. Цена:

* вызывающему нужен **root**;
* старт — это `platform_detect()` с `dumpsys SurfaceFlinger` (секунды) до первого полезного
  действия;
* при установленном Magisk-модуле или живом приложении проверка занятости порта 50505 должна
  отправить команду уже работающему демону; если проверка не сработает — **второй демон**, драка
  за режим и за порт (второй `bind` просто упадёт, часть команд потеряется молча).

| | A: пассивный демон + `burst` | B: старт процесса по кнопке |
|---|---|---|
| Нужен root вызывающему | нет | да |
| Задержка до первого действия | нет (демон уже разведан) | секунды (`platform_detect`) |
| Второй демон | нет | да, если живёт модуль или приложение |
| Кто может вызвать | любое приложение, shell, настройки прошивки | только root/`su` |
| CPU в покое | один `poll` раз в 300 мс | ноль |

Про Android 12+: ограничение на фоновый старт foreground-службы касается приложений с
`targetSdk 31+`; у AFRd2 `targetSdk 28`, так что сама форма A под него не попадает. Но маппер
кнопок — чужое приложение, и его право стартовать процессы/службы мы не контролируем; поэтому
форма A (демон уже работает) надёжнее.

Вывод: **A — основной путь**, B — дополнительный, только для Magisk-пользователей без приложения.
Код сеанса у обеих форм общий.

## 4. Как получить «одно переключение»

Механики, которые в сеансе надо погасить (ключи — `config/afrd2.ini`, проверка — `cfgkeys.c`):

| Механика | В сеансе | Почему |
|---|---|---|
| `switch.bump` — подъём до максимума ТВ при старте видео | **выключить** | смысл только до первого кадра плеера; посреди сессии — лишнее мигание |
| «лечение подачи» (`fps.cadence.fix.ms`, `afrd.c:3773`) — режим туда-обратно | **выключить** | два лишних переключения подряд |
| `switch.ceiling.reset` — перезапуск кодека | только плеерам из `switch.bump.pkg` | перезапуск кодека — не мигание, но сбой картинки; нужен там, где плеер зажал темп |
| `fps.recheck.delay.ms` — перепроверка замера через 4 с | **вопрос** | исправляет ошибку замера, но это второе переключение |

Итог сеанса: одно переключение (плюс, у зажатого плеера, один перезапуск кодека). Это ровно то,
что просил SlimBOX.

## 5. Длительность и условия выхода

По умолчанию (`config/afrd2.ini`): прогрев `fps.measure.envelope.skip.ms=2000`, решение по
огибающей `fps.measure.envelope.ms=20000` (раннее — `early.ms=14000`), предел наблюдения
`max.ms=30000`, плюс само переключение ~0.5 с.

Отсюда два варианта умолчания `burst.ms`:

* **40000 мс** — покрывает худший случай (`skip` + `max` + переключение); рекомендую;
* **30000 мс** — покрывает обычный случай (решение на 14–20 с), но на «неоднозначном» контенте
  сеанс истечёт до решения — переключения не будет вовсе.

Допуск: 15000–120000 мс.

Сеанс заканчивается по первому из событий:

* истёк срок;
* видео остановилось (декодер исчез) — возврат сразу, дедлайн не ждём;
* пауза дольше `switch.delay.off` (в сеансе трактуем как конец; при `0` — ждём до срока);
* пришла команда `burst 0` (отмена).

Повторная команда **продлевает** срок, а не запускает второй сеанс.

## 6. Как внешнее приложение запускает сеанс

Мапперы кнопок умеют разное, поэтому предлагаю четыре интерфейса; это дешево, и они не мешают
друг другу.

| Интерфейс | Кому | Root | Что нужно на стороне бокса |
|---|---|---|---|
| **UDP** `burst <ms>` на `127.0.0.1:50505` | скрипты, настройки прошивки, свои приложения | нет | только демон |
| **Broadcast** `ru.reyter.afrd2.action.BURST`, extras `ms` / `cancel` | Button Mapper, tvQuickActions | нет | установленное приложение AFRd2 |
| **Activity** `ru.cobra.afrd.BURST` + extra `ms` | tvQuickActions (запуск activity), любые лаунчеры | нет | установленное приложение AFRd2 |
| **Shell** `afrd --burst 40` | Magisk-модуль без приложения | нет для команды; root — если демона нет и его надо поднять | бинарник в `PATH` |

Детали:

* UDP — формат как у остальных команд API: строка, аргумент через пробел, ответ можно не читать.
  Проверка: `echo 'burst 40000' | timeout 2 nc -u -w1 127.0.0.1 50505` (toybox `nc` не
  завершается после ответа — отсюда `timeout`, код 124 — норма; если `nc` нет вовсе, используйте
  broadcast).
* Broadcast — приёмник в приложении пересылает команду демону. Отправитель должен указать пакет
  (`setPackage("ru.reyter.afrd2")`) или компонент: так broadcast не считается неявным и доходит на
  Android 8+. Проверка из shell:
  `am broadcast -a ru.reyter.afrd2.action.BURST --ei ms 40000 -p ru.reyter.afrd2`.
* Activity — расширение уже существующего `ActionActivity` (там же `ru.cobra.afrd.START`/`.STOP`),
  extra `ms`; для tvQuickActions это самый простой путь без root.
* Shell — `afrd --burst <ms>` только шлёт команду живущему демону; `--burst` без демона и с root
  поднимает его на время сеанса (форма B).

## 7. Что нужно от прошивки

1. **Назначение кнопки.** Либо пункт в настройках slimBOXtv («AFR по кнопке»), либо инструкция для
   сторонних мапперов. Технически достаточно любого из четырёх интерфейсов выше.
2. **Обратная связь.** Пользователь нажимает и до 14–20 с ничего не видит. Нужен тост/индикация
   («AFR: 24 Гц, 40 с») или хотя бы мгновенный отклик маппера.
3. **Тест на живом боксе.** Проверить: сеанс при выключенном AFR; повторное нажатие (продление);
   отмену; возврат режима после сеанса; отсутствие лишних миганий.

## 9. Риски и ограничения

* Порт API слушает только loopback, но `burst` может послать **любое** приложение на боксе. При
  необходимости — лимит частоты и/или токен в конфиге.
* Если одновременно живут Magisk-модуль и приложение, в системе уже сейчас два демона; сеанс это не
  усугубляет, но команду примет только захвативший порт (второй `bind` падает — видно в журнале).
* У плееров со своим AFR (OTT Navigator) сеанс переключит режим под уже идущий поток — как обычный
  старт AFR посреди сессии; сброс потолка им не положен (§81).
* Перезапуск кодека при сбросе потолка действует на **все** приложения сразу: фоновое
  воспроизведение в другом приложении прервётся.
* Сеанс не должен ломать сторож приложения: он считает живым демон с растущим heartbeat, пассивный
  цикл heartbeat обновляет.
