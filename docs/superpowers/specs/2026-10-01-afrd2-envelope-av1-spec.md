# AFRd2: устойчивая оценка частоты кадров (нижняя огибающая) и кодековая поправка (AV1)

Дата: 2026-10-01. Статус: **спека утверждена владельцем** (решения ниже), реализация — по плану
`docs/superpowers/plans/2026-10-01-afrd2-envelope-av1.md`.

Относится только к новому пути демона (Android 10–14, `run_atv14()`). Legacy-путь (Android 6–9)
не меняется.

## 1. Задача

Жалоба владельца: на YouTube (штатный клиент, AV1) 24-фпс ролики уезжают в 25/50 Гц, а у границы
класса режим «мигает» (переключение туда-обратно), что видно глазом.

Причина измерена: счётчик кадров декодера `vdec_status` завышен, причём:

* завышение **аддитивное** (кадр/с), а не процентное;
* у него две составляющие — кодек (AV1-тракт декодера) и плеер (подача кадров);
* разброс завышения внутри класса (±0.5 кадра/с) **больше зазора между классами 24 и 25 (1.0 кадра/с)**.

## 2. Измерения (2026-10-01, стенд 192.168.88.50, Android 14, S905X5M)

### 2.1. Кодековая составляющая (тот же файл, один плеер)

Sintel `24.000 fps`, Just Player (Legacy) 0.217, `armeabi-v7a`, аппаратное декодирование
(ExoPlayer → MediaCodec → Amlogic V4L2), выборка счётчика раз в секунду, 20 с на файл:

| файл | декодер | замер |
|---|---|---|
| `sintel24.mp4` (H.264) | `ammvdec_h264_v4` | **24.002 / 23.929 / 24.089** |
| `sintel_av1.mp4` (AV1) | `amvdec_av1_v4l` | **24.520 / 24.532** |

Оба файла проверены независимо (`r_frame_rate = avg_frame_rate = 24/1`; 718 и 720 кадров за 30 с).
Вывод: **AV1-тракт завышает счётчик на ≈ +0.5 кадра/с** (n=3/2), H.264 — точен.

### 2.2. Клиентская составляющая (штатный YouTube, 65 роликов + 13 роликов сэмплером)

Номиналы — по `yt-dlp -J`; режим жёстко `1080p60hz`, демон выключен, ΔF/Δt за 10 с (65 роликов)
и раз в секунду по 30 с (13 роликов). Кодеки: AV1 (`amvdec_av1_v4l`), VP9 (`amvdec_vp9_v4l`),
H.264 (`ammvdec_h264_v4`).

| оценка (порог класса 24 ↔ 25 = 24.4898) | верно 24 fps | верно 25 fps |
|---|---|---|
| среднее за 10 с, 65 роликов, без поправки | 30.3 % | 93.8 % |
| то же, поправка −0.5 для AV1 | 51.5 % | 93.8 % |
| то же, поправка −1.05 для AV1 | 87.9 % | 84.4 % |
| среднее за 30 с, 13 роликов, без поправки | 14 % | 100 % |
| **мин по скользящим 5-с окнам, 20 с, без поправки** | **86 %** | **100 %** |
| мин, 15 с | 71 % | 100 % |
| мин + поправка −0.5 для AV1, 15–30 с | 86–100 % | 50–67 % |

Отдельно: VP9 и H.264 измеряются верно (23.81…24.33 и 25.00), завышает только AV1;
`frame dur` на AV1-пути всегда 3200 (30 fps) — бесполезен; на H.264 бывает двойка (24 fps → 2000).

### 2.3. Почему огибающая

Завышение односторонне: плеер повторно декодирует кадры на границах DASH/HLS-сегментов, AV1-тракт
добавляет свои — **но ничто кадры не отнимает**. Значит истинная частота ≈ минимум наблюдённой по
подокнам; шум и повторные кадры поднимают отдельные подокна, но не опускают все. Проверено и на
живом IPTV-потоке (23.976 по PTS против 24.56 по счётчику).

Огибающая **заменяет** поправку, а не дополняет её: с ней поправка −0.5 только ухудшает 25-фпс
класс (50–67 %). Поэтому поправка остаётся опциональным инструментом для плееров с большим
смещением, по умолчанию выключенным.

## 3. Решения владельца (2026-10-01)

1. **Поправка на AV1 внедрена** (ключ + логика + GUI-пункт). Исходно — выключенной по умолчанию;
   **уточнение владельца 2026-10-01 (после живой демонстрации): включена по умолчанию со значением
   0.3** — см. решение 3.
2. **Ждать устойчивой оценки: один точный переход** вместо быстрого, но ошибочного решения.
   Первые секунды видео режим остаётся прежним.
3. **Правило при неоднозначности (уточнение владельца, 2026-10-01):** ошибка «24 fps определён как
   25 Гц» предпочтительнее обратной («25 fps определён как 24 Гц») — пропуск кадра заметнее повтора.
   Следствия:
   (а) при неоднозначном доверительном интервале решение берётся по следующему по медленности
   решаемому окну, то есть в сторону класса 25, а не «решение не принято» (см. §4.1 и ruling R6);
   (б) рекомендуемое значение `fps.correct.av1.offset` — **0.3** кадра/с: на 13 живых записях
   (штатный YouTube, AV1) оно исправляет один 24-фпс ролик и не переводит ни один 25-фпс в 24 Гц;
   значение 0.5 этому правилу противоречит — на живой серии честный 25-фпс ролик (`z7do1hhb6fE`)
   ушёл в `1080p24hz` (журнал §16.7). Итоговое решение владельца: поправка **включена по умолчанию
   со значением 0.3** (`fps.correct.enable=1`, `fps.correct.av1.offset=0.3`).

## 4. Что именно реализуется

### 4.1. Нижняя огибающая (`fps_env.h/.c`)

* Демон копит выборки `(t, frame count, длительность чтения)` из того же `vdec_poll`, что и сейчас
  (одно чтение за итерацию цикла, доп. нагрузки нет).
* Решение принимается по **минимуму частоты среди подокон** длиной `sub.ms` (5 с), начало подокон —
  не раньше `skip.ms` (2 с, прогрев: замер после старта потока бывает заниженным), горизонт
  наблюдения — `envelope.ms` (20 с), предел расширения при неоднозначном доверительном интервале —
  `envelope.max.ms` (30 с).
* Подокно, внутри которого счётчик не рос (пауза/буферизация), не рассматривается; сброс счётчика
  (новое видео) начинает наблюдение заново.
* Классификация — существующая (`fps_classify_window`: ±1 кадр и неопределённость меток времени
  должны уложиться в одну группу частот).
* Ключи: `fps.measure.envelope.ms`, `fps.measure.envelope.max.ms`, `fps.measure.envelope.sub.ms`,
  `fps.measure.envelope.skip.ms`. Ключи `fps.measure.window.ms` / `fps.measure.window.max.ms`
  устаревают (остаются известными, аудит конфига называет их устаревшими).

### 4.2. Кодековая поправка (`fps.correct.av1.*`)

* `fps.correct.av1.offset` — аддитивная поправка в кадрах/с (0 — выключено);
  `fps.correct.av1.pkg` — ограничение по пакету плеера (пусто — любой).
* Применяется к частоте подокна до классификации, только при `fps.correct.enable=1` и только если
  `device name` из `vdec_status` содержит `av1`.
* С точки зрения продукта это «инструмент для конкретного плеера»; рекомендуемое значение при
  включении — 0.5 (измерено на AV1-тракте).

### 4.3. Что НЕ меняется

* Legacy-путь (Android 6–9), приёмник (backdoor 1035), триггер (`vdec_status`), возврат режима,
  API, пауза, `mode.prefer.exact`, `mode.use.fract`, `mode.blacklist.rates`,
  `fps.declared.crosscheck.pct` (уточнение по `frame dur` остаётся) — как есть.
* Подсказка плеера (`frame_rate_hint`, `fps.prefer.api`) по-прежнему применяется мгновенно:
  она точная, и ждать наблюдения для неё не нужно.

### 4.4. Следствия

* Латентность: первое переключение — примерно через `skip.ms + envelope.ms` ≈ 22 с после старта
  видео (было 1.5–6 с). Для файлов и потоков это незаметно, для клипов короче горизонта — режим
  просто не переключается.
* Перепроверка (`fps.recheck.delay.ms`) остаётся, но с огибающей измеряет заново (свой горизонт).
* Ожидания смоук-матрицы стенда (`HOLD_WAIT`) увеличиваются под новую латентность.

## 5. Приёмка

1. Хостовые тесты (в т.ч. на фикстурах — реальных записях счётчика: 24-фпс AV1 (верный и
   «завышенный» ролики), 25-фпс AV1, VP9, 60-фпс синтетика, пауза, сброс счётчика).
2. Живой прогон на стенде: клипы 23.976/25/50 → `1080p24hz`/`1080p50hz`/`1080p50hz`; задержка
   переключения ≈ 20–23 с; отсутствие второго перехода в течение минуты.
3. YouTube (штатный клиент, AV1): без поправки — один переход (24-фпс ролик → 25/50 Гц, без
   «перескока»); с `fps.correct.av1.offset=0.5` — 24-фпс ролик → `1080p24hz` одним переходом.
4. Пауза/возобновление и смена ролика: наблюдение начинается заново, «залипшего» решения нет.
