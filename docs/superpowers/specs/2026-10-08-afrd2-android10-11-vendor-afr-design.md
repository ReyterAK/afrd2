# AFRd2: AFR на Android 10/11 через вендорный SystemControl + быстрый путь по заявленной частоте

**Дата:** 2026-10-08
**Стенды:** `.45` (Amlogic X4, Android 11, ядро 5.4.125, Magisk) — основной для этой работы;
`.50` (ATV14) и `.76` (ATV9) — предоставляются владельцем после обкатки на 11.

## 1. Цель

Довести AFRd2 до рабочего состояния на Android 10/11 и ускорить решение о режиме до уровня
системного AFR.

Сейчас на этих версиях демон уходит в **пассивный режим** (переключать нечем: транзакция
SurfaceFlinger 1035 там значит другую операцию, а запись в `/sys/class/display/mode` переключает
выход без синхронизации фреймворка). При этом AFR на этих боксах **работает** — вендорным
механизмом Amlogic, и он заметно быстрее нашего:

| | Системный AFR | AFRd2 (сегодня) |
|---|---|---|
| Источник частоты | строка `frame rate` из `vdec_status` (заявленная драйвером) | замер по росту `frame count`, нижняя огибающая подокон |
| Реакция 23.976 | **2–4 с** → `1080p24hz` | 16–22 с (`fps.measure.envelope.early.ms` 14000 / `fps.measure.envelope.ms` 20000 + прогрев 2000) |
| Реакция 25 | **4–6 с** → `1080p50hz` | то же окно |
| Точность | целое (`24`, `25`, `30`) | точная (23.976) |
| На синтетическом клипе 23.976 | заявлено `30`, **не переключил вовсе** | переключит верно (замер) |

Отсюда две задачи: (1) научить демон **применять** режим на 10/11 вендорным механизмом;
(2) перенять у системы **быстрый путь** — решение по заявленной частоте с последующей проверкой
замером, чтобы получить скорость системы и надёжность нашу.

### Критерии успеха

1. На `.45` клип 23.976 приводит к `1080p24hz` (и `vinfo`/SF на 23.976) **за ≤5 с** от старта.
2. Клип 25 → `1080p50hz`; клип 60 → `1080p60hz`; на остановке — возврат в исходный режим.
3. Синтетический клип (драйвер заявляет 30 при фактических 23.976) **исправляется** замером:
   после огибающей режим приводится к 24 Гц, в журнале видно «заявлено X, замер дал Y».
4. ATV14 не меняет поведения по умолчанию (быстрый путь там выключен).
5. `sh tests/run_tests.sh` — зелёный; новые host-тесты покрывают класс из заявленной частоты,
   выбор режима по имени и приоритет замера.

## 2. Не-цели

- Поддержка Android 10/11 на не-Amlogic железе (механизм вендорный; при отсутствии сервиса —
  прежнее поведение, пассивный режим с предупреждением).
- Замена замера огибающей на заявленную частоту: замер остаётся источником истины, быстрый путь —
  только предварительное решение.
- Изменение поведения ATV14 по умолчанию (быстрый путь там выключен до отдельной проверки).
- GUI для новой настройки сверх строки в существующей группе «Тонкая настройка Android 12+»
  (строка добавляется, новых экранов нет).

## 3. Ограничения (проверено на `.45`)

1. **Вендорный механизм:** `vendor.amlogic.hardware.systemcontrol@1.1::ISystemControl`,
   метод `setActiveDispMode(String)` — принимает **имя** режима (`1080p24hz`). Сервис зарегистрирован
   (`lshal`), реализация — `/vendor/bin/systemcontrol`. Клиент собирается **без** HIDL-заголовков:
   классы прокси лежат в `/system_ext/priv-app/droidlogic-res/droidlogic-res.apk`, вызов идёт
   штатным `app_process` (готовый помощник — `tools/droidlogic/`, проверен живьём).
2. **Синхронность:** вендорный путь держит SurfaceFlinger в синхроне (после `setActiveDispMode`
   меняются и `vinfo`, и `refresh-rate` в дампе SF). Запись в `/sys/class/display/mode` — **не**
   держит (нужен `debug=1`, SF остаётся на прежней частоте): этот путь не используем.
3. **Транзакция 1035 на сборке 11 небезопасна**: вызов с одним `int` роняет SurfaceFlinger
   (наблюдалось: перезагрузка бокса). В новой ветке она не вызывается вообще.
4. **Замер на 5.x:** в `vdec_status` есть только `frame rate`, `frame dur`, `frame count`,
   `frame height`; узлов `vdec_chunks`/`vdec_blocks` **нет** → legacy-алгоритм замера неприменим,
   замер остаётся ATV14-й (поллинг + огибающая). `frame rate` на 5.x бывает мусором (см. §1).
5. **Список режимов:** имена режимов и их поддержка — в `/sys/class/amhdmitx/amhdmitx0/disp_cap`;
   дробность — `/sys/class/amhdmitx/amhdmitx0/frac_rate_policy`; активный режим — `/sys/class/display/mode`.
6. **Определение пути** (как `platform_detect()`): legacy — есть `/sys/class/switch/hdmi/*`;
   новый путь — есть `vdec_status` и нет старых узлов. Внутри нового пути backdoor проверяется
   пробным вызовом 1035 (`sf_backdoor_available`).

## 4. Архитектура

Один цикл решения (`run_atv14`) на все платформы; различия вынесены в две точки — **выбор режима**
и **применение**.

### 4.1. Компоненты

| Компонент | Ответственность | Файл |
|---|---|---|
| Определение платформы | новый вид `PLAT_ATV11`: новые узлы + нет backdoor + **есть** вендорный SystemControl | `platform.c` |
| Вендорный sink | применение режима **по имени** через помощник; снятие — no-op | `sink.c`, `sink.h` |
| Выбор режима | ATV11 — по имени из `disp_cap` (разбор и рейтинг legacy); ATV14 — по id таблицы SF | `afrd.c` (функция выбора), `modes.c` |
| Быстрый путь | решение по заявленной частоте сразу, пометка «предварительное» | `afrd.c` |
| Настройка | `fps.declare.fast` (0/1) | `cfg.c`/`cfgkeys.c`, профили, GUI |

### 4.2. Определение платформы

В `platform_detect()` после существующих проверок:

```
have_vdec && !have_old_hdmi  →  новый путь:
    if (backdoor доступен)          → PLAT_ATV14, sink = SINK_SF_BACKDOOR   (как сейчас)
    else if (вендорный SystemControl есть) → PLAT_ATV11, sink = SINK_VENDOR_MODE
    else                            → PLAT_ATV14 + пассивный режим          (как сейчас)
```

«Вендорный SystemControl есть» = существует `/vendor/bin/systemcontrol` **и**
`/system_ext/priv-app/droidlogic-res/droidlogic-res.apk` **и** помощник (`vendor_disp_cli`).
Путь к помощнику берётся из конфига (ключ `vendor.disp.cli`, умолчание
`/data/local/tmp/afrd-disp.sh`), потому что приложение и Magisk-модуль раскладывают его в свои
каталоги.

В `platform_t` добавляются: `const char *disp_cap;` (`/sys/class/amhdmitx/amhdmitx0/disp_cap`),
`const char *vendor_mode_cli;`.

### 4.3. Sink

```c
typedef enum {
    SINK_LEGACY = 0,        /* запись имени в /sys/class/display/mode (Android 6-9) */
    SINK_SF_BACKDOOR = 1,   /* service call SurfaceFlinger 1035 i32 <id> (Android 12-14) */
    SINK_VENDOR_MODE = 2,   /* app_process: ISystemControl.setActiveDispMode(<имя>) (10/11) */
} sink_kind_t;
```

- `sink_apply(SINK_VENDOR_MODE, mode_path, sf_id, legacy_mode_name)`: собирает команду
  `sh <cli> <имя>` и выполняет; требует `legacy_mode_name != NULL` (имя), `sf_id` игнорирует.
  Возврат: 0 — помощник отработал (код 0), -1 — иначе.
- `sink_release_backdoor(SINK_VENDOR_MODE)`: no-op (возврат 0). Режим держит не флаг, а вендорный
  сервис; «снятия удержания» как понятия здесь нет — возврат делается обычным применением
  исходного режима.
- Тесты: `tests/test_sink.c` расширяется — сборка команды, отказ при отсутствии имени,
  no-op снятия.

### 4.4. Выбор режима

Внутри цикла решение о целевом режиме различается, применение — одинаково (через sink).

- **ATV14** (как сейчас): таблица режимов SF, `sfmodes_select()` по классу частоты + разрешению,
  результат — `id` для транзакции.
- **ATV11**: список из `disp_cap` (переиспользуем разбор legacy-профиля: имена, геометрия,
  частоты), выбор **legacy-рейтингом** (удвоение 25→50 при `mode.prefer.exact=0`, точное
  совпадение при 1, чёрный список `mode.blacklist.rates`), результат — **имя** режима
  (`1080p24hz`). Реализуется функцией, возвращающей пару «имя + частота», плюс `id = -1`.

Единая точка решения отдаёт структуру:

```c
typedef struct {
    int  sf_id;          /* для SINK_SF_BACKDOOR; -1 для режима по имени */
    char name [32];      /* для SINK_LEGACY и SINK_VENDOR_MODE */
    int  hz;             /* выбранная частота, 24.8 */
} mode_target_t;
```

### 4.5. Быстрый путь по заявленной частоте

Ключ `fps.declare.fast`, умолчание: **1 для `PLAT_ATV11`**, **0 для `PLAT_ATV14`**
(в профиле `config/afrd2.ini` — `fps.declare.fast=0`; для ATV11 значение подставляется в
`afrd_run` так же, как это сделано для `switch.delay.off`).

Логика в цикле:

1. Новое видео замечено (существующие дебюсы `trigger.start.debounce.ms`).
2. Если `fps.declare.fast` и `vdec_status.frame rate` даёт приличное значение (> 0, известный класс):
   - выбрать режим под этот класс и **применить сразу**;
   - пометить состояние как `decided_fast = true`, запомнить `fast_class`;
   - в журнал: `быстрое решение по заявленной частоте: X Гц (fps.declare.fast)`.
3. Огибающая продолжает мерить (как сейчас). Когда замер даёт класс:
   - совпал с `fast_class` → ничего не делаем (решение подтверждено);
   - разошёлся → применяем режим по замеру (существующий путь перепроверки `fps.recheck.delay.ms`
     уже перемеряет через 4 с), в журнал: `заявлено X Гц, замер дал Y Гц — правлю режим`.
4. `fps.declare.fast=0` → поведение прежнее (решение только по огибающей).

Заявленная частота — **целое** (`24`, `25`, `30`), поэтому класс берётся существующим `fps_class`
(он группирует 23.976/24.00 и 29.97/30.00 в один класс), а точный представитель класса — из
профиля/резолвера (`mode.prefer.exact`, дробность).

### 4.6. Поток данных

```
                ┌──────────────── fps.declare.fast=1 ───────────────┐
vdec_status ──► │ frame rate (заявл.) ─► класс ─► выбор режима ─► sink ─► режим (2-4 с)
                └───────────────────────────────────────────────────┘
        │
        └─────► frame count ─► огибающая ─► класс ─► расхождение? ─► переприменение (16-22 с)
```

### 4.7. Упаковка помощника

- В репозитории: `tools/droidlogic/{AfrdDispMode.java,afrd-disp.sh,build-dex.sh}` (уже есть),
  артефакт `afrd-disp.dex` собирается ими.
- В APK: `assets/droidlogic/afrd-disp.dex` и `afrd-disp.sh`; приложение при старте раскладывает их
  в `cacheDir` и передаёт путь ключом `vendor.disp.cli`.
- В Magisk-модуль: файлы в `system/etc/afrd/`, `service.sh` раскладывает и передаёт путь.
- На время отладки на `.45` допускается `/data/local/tmp/afrd-disp.sh` (умолчание конфига).

## 5. Поведение и краевые случаи

| Случай | Поведение |
|---|---|
| Вендорного сервиса нет | `PLAT_ATV14` + пассивный режим (как сегодня), в журнале предупреждение |
| Помощник есть, но вернул не 0 | предупреждение в журнал, режим не меняем; повтор на следующем решении |
| `frame rate` = 0 или класс неизвестен | быстрый путь пропускается, работаем по огибающей |
| Заявленная частота врёт | быстрый путь даст ложный режим, замер исправит; в журнале обе строки |
| Режим уже нужный | sink не вызывается (`mode_target` равен текущему) |
| Пауза/возобновление | как сейчас (`pause.c`, `switch.delay.off`); быстрый путь не влияет |
| Остановка видео | возврат исходного режима обычным применением (для ATV11 — `setActiveDispMode(исходный)`) |
| `disp_cap` пуст/нечитаем | нет списка режимов → пассивный режим с предупреждением |

## 7. Приёмка

**Host-тесты:** класс из заявленной частоты (24/25/30 и их дробные представители); выбор режима по
имени из `disp_cap` (удвоение 25→50, точное при `mode.prefer.exact=1`, чёрный список); приоритет
замера при расхождении; пропуск быстрого пути при мусорной заявленной частоте; сборка команды
вендорного sink и no-op снятия.

**Живой прогон на `.45`** (обязателен до передачи `.50`/`.76`):

| Проверка | Ожидание |
|---|---|
| 23.976 (реальный контент) | `1080p24hz` за ≤5 с, `vinfo`/SF 23.976 |
| 25 (реальный) | `1080p50hz` за ≤5 с |
| 60 | `1080p60hz` |
| синтетика 23.976 (заявлено 30) | сначала 30-й класс, после огибающей — исправление на 24; обе строки в журнале |
| стоп | возврат исходного режима |
| `fps.declare.fast=0` | поведение прежнее (только огибающая) |
| вендорный помощник недоступен (переименовать dex) | предупреждение в журнал, режим не трогается |
| `disp_cap` пуст/нечитаем | пассивный режим с предупреждением, без падений |

**Регрессия ATV14** — только после предоставления `.50`; до этого код ATV14 проверяется host-тестами.

## 8. Риски

| Риск | Смягчение |
|---|---|
| Быстрый путь даёт ложный режим на испорченной заявленной частоте | замер продолжает работать и правит режим; обе строки в журнале; на ATV14 путь выключен |
| Правка ядра цикла задевает ATV14 | быстрый путь — отдельная ветка под ключом; при `0` код идёт прежним путём; host-тесты + будущий прогон `.50` |
| Помощник (dex+app_process) не запустится после обновления прошивки | явный лог и пассивный режим; путь к dex встраивается в APK/модуль, а не берётся из системы |
| Два механизма (вендорный и наш) подерутся за режим | системный AFR останется включённым у пользователя; демон ставит режим, системный может переставить — на `.45` проверить вместе (владелец может выключить `autoframemode`) |

## 9. Открытые вопросы

1. Гасить ли системный AFR (`persist.sys.autoframemode`) при работе AFRd2, или допускать их
   сосуществование (решить по итогам живого прогона).
2. Нужна ли строка настройки `fps.declare.fast` в GUI для Android 10/11 (сейчас планируется в
   существующей группе «Тонкая настройка Android 12+»).
3. Оставлять ли `vendor.disp.cli` в конфиге пользовательским (для отладки) или только внутренним.
