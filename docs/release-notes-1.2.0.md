## AFRd2 1.2.0

Автоподбор частоты обновления HDMI под частоту кадров видео для Amlogic.
Форк [AFRd](https://github.com/anpaza/afrd) 0.3.2 (Андрей Заболотный, anpaza), GPL-3.

### Новое

* **AFR «по требованию».** Обычно автоподбор выключен, а по команде извне демон
  включается на время сеанса, делает одно переключение, возвращает прежний режим и
  снова выключается. Команда API `burst <мс>`, broadcast
  `ru.reyter.afrd2.action.BURST`, activity `ru.cobra.afrd.BURST` или утилита
  `afrd --burst <с>`; сеанс принимается и при `enable=1`.
* **«Авто» в политике дробных частот стало настоящим.** Целая частота берётся
  только когда источник заявил целую (frame rate hint: 24.000 против 23.976, или
  заявленная длительность кадра: 96000/4000 против 96000/4004), иначе остаётся
  дробный представитель. Заявка из чужой группы (драйвер рапортует 30 fps при
  реальных 23.976) игнорируется.
* **Проверка фактической частоты** после смены режима: демон читает
  `sync_duration_num/den` из `vinfo` через 2.5 с и пишет в журнал
  «фактическая частота дисплея: 23.98 Гц (vinfo 23976/1000)».
* **Сверка источников частоты**: если видео-слой обновляется заметно реже решения
  по счётчику кадров, в журнал идёт одна строка со счётчиком, подачей, заявленной
  частотой и состоянием декодера.
* **Короткий спуск после подъёма** (`switch.bump.probe.ms`, 2500 мс, 0 — выключить):
  раньше решение ждало огибающую 14–31 с, всё это время экран работал на максимуме;
  теперь через 2.5 с и далее раз в секунду режим выбирается по данным видео-слоя.
* **`switch.revert`**: если подача после переключения осталась зажатой и лечение
  «туда-обратно» не помогло, режим возвращается к прежнему (22 % → 0 % выбросов,
  ценой потери части кадров контента).
* **Сброс «потолка» — отдельный список** `switch.ceiling.pkg` (в приложении —
  «Плееры, которым сбрасывать потолок», по умолчанию только YouTube):
  перезапуск кодека рвёт сессию OTT Navigator, а подъём режима ему полезен —
  поэтому списки разные.
* **Вердикт подачи по доле выбросов** (`fps.feed.ratio.pct` / `fps.feed.gap.pct`),
  а не только по медиане: рваная подача больше не проходит как «подача в порядке».
* **OTT Navigator на Android 10+ исключён по умолчанию** (`switch.skip.pkg`): он сам
  управляет частотой через `Surface.setFrameRate`. В 1.1.0 список был пуст, и демон
  с ним конфликтовал. На Android 6–9 поведение не менялось.
* **Системный режим на рабочем столе** (`switch.restore.preferred`, по
  умолчанию включён, Android 10–14): при выходе на рабочий стол возвращается
  режим, выбранный в настройках Android TV, а не режим прошлого видео.
  Выключено — прежнее поведение (режим до видео). На Android 6–9 ключ не
  действует.
* **Настройки без дублей**: поправка AV1 — один пункт (в приложении только
  «Выключено», своё значение — в ini) плюс список плееров, к которым она
  применяется; поведение на паузе — один пункт («На паузе»); ключи, не
  действующие на текущем пути, скрыты, а не погашены. Автопоправки AV1 по
  платформе больше нет: поправка действует только на плееры из списка, пустой
  список — не применяется (встроенный список пакетов требовал пересборки на
  каждого нового плеера — решение по §178).
* **Тише журнал**: повторяющиеся строки ограничены по частоте; при расходящихся
  значениях одного ключа в конфиге пишется «дубль ключа …, действует последнее».
* **Поле «Тестеры» в «О программе»** (как в оригинальном AFRd): Acorn@4PDA,
  SlimHouse@4PDA, valerash88@4PDA; на 4PDA в шапке темы — спойлер «Благодарность
  тестерам».
* **«Возвращать цветовой профиль»** (`cs.restore`, умолчание `1`): когда демон
  возвращает режим (конец видео, уход плеера с переднего плана), он пишет обратно
  формат, который был до переключения. Без этого широкое правило (`.*=422`)
  остаётся и на рабочем столе — текст в интерфейсе размывается по хроме.
  На ATV14 текущее значение читается вендорским клиентом
  (`meson_display_client -g "HDMI Color ATTR"`): узел `attr` там не отражает то,
  что выставил клиент. На старом пути — из `cs.path`.
* **«Не изменять формат»** — первый пункт настройки «Формат HDMI»: пустой
  `cs.select`, демон не пишет формат ни разу (ни по правилу, ни по «умолчанию»).
  В 1.1.0 такого пункта не было — список состоял только из политик с правилом
  защиты 4K, а пустой набор правил в коде означал «применить умолчание», то есть
  запись при каждой смене режима. Умолчанием осталось «Авто».

* **Частота по подаче видео-слоя.** У плееров на Android 10–14 (штатный
  YouTube, TizenTube/Cobalt) метки `actualPresentTime` слоя различают 23.976 и
  25.000 к/с там, где счётчик кадров декодера завышен: на 24p он показывал
  25.00, и режим уходил в 25/50 Гц. Демон сверяет окно слоя со счётчиком и при
  расхождении берёт слой — «частота по подаче видео-слоя: 23.98 Гц вместо
  25.00 Гц по счётчику — беру слой». Живой замер (ATV14, дисплей 60 Гц): 24p —
  режим 24 Гц, 25p — 50 Гц. Проба — два `dumpsys` (~100 мс) на решение, средний
  интервал между решениями 14–20 с, демон 0.1 % CPU. Плееры без меток слоя
  (VLC, Just Player) обслуживаются как раньше.

* **Реклама в начале ролика не портит замер** (переход контента). Окно подачи
  слоя режется по времени на половины и сравниваются классы частот (30 против
  24); при смене класса замер, закрепление частоты и флаги сбрасываются, решение
  откладывается до чистого горизонта, не больше трёх сбросов на видео. Своя
  смена режима переходом не считается.

* **Мини-приложение «AFR burst»** (`ru.reyter.afrd2.burst`, отдельный APK) для
  мапперов кнопок: одна кнопка — один сеанс, без extras и action. Своя иконка и
  баннер (горчичный `#C9A128` вместо синего `#1B3A6B`), категория
  `LEANBACK_LAUNCHER` — иначе TV-мапперы пакет не показывают.

* **Фактические частоты в списке запретов.** На Android 6–11 имя режима одно на
  24.000 и 23.976 (`1080p24hz`), а что реально отдаёт прошивка, пассивно узнать
  нельзя: `disp_cap` перечисляет имена, `vinfo` знает только текущий тайминг.
  Появилась проба «Проверить дробные частоты» (экран мигнёт дважды): после неё
  список подписан тем, что режим отдаёт на самом деле — 23.976 / 29.97 / 59.94
  (или «23.976 / 24», если драйвер держит целую). До пробы показывается номинал,
  результат кешируется с датой (`FracProbe`, `RatesProbe`,
  `tests/FracProbeTest.java`).

### Исправлено

* **`switch.skip.pkg` не запрещал смену режима** на новом пути с 1.0.0: гейт стоял
  после быстрого решения, и плеер из списка «AFR мешает» всё равно получал
  переключение. Теперь для него не работают ни замер, ни быстрое решение, ни
  перепроверка, ни переприменение.
* **Рабочий стол больше не остаётся на частоте видео** у плееров из «Устранять
  зажим»: возврат режима при выходе плеера с переднего плана и на паузе снова
  работает (`player_left_fg` / `pause_restore`), строка «плеер ушёл с переднего
  плана — возвращаю режим» больше не повторяется.
* **Замер мог увести режим вниз на живом видео**: на канале 1080i50 счётчик кадров
  задушен режимом и завышен плеером (OTT отдаёт кодеку frame-rate=30), и «нижняя
  огибающая» уводила 50 → 30. Теперь принятая частота — нижняя граница, но только
  при кратности заявленной (2×/3×, допуск 4 %): 50 против 25 — да, 25 против 24 —
  нет. Микроперезапуск декодера (OTT пересоздаёт его каждые 20–50 с) границу не
  сбрасывает: 90 с на 50 Гц без переключений.
* **Поправка AV1 применялась дважды**, если были заданы и проценты, и смещение:
  контент 25.000 измерялся как 24.90. Теперь модель выбирает демон по платформе,
  старые ключи читаются взаимоисключающе.
* **На стыке роликов на одну смену режима меньше**: плеерам из «Устранять зажим»
  режим не возвращается сразу, а поднимается на старте следующего ролика; возврат —
  когда плеер уходит с переднего плана.
* **Замер замирал после решения, совпавшего с текущим режимом**: на 1080i50 режим
  мог остаться на 60 Гц до конца видео (в журнале — 109 с без единого замера), а
  сразу после смены канала 1 -> 210 демон держал 60 Гц десятки секунд и делал
  лишние переключения. Теперь замер продолжается, таймер «счётчик кадров не
  растёт» сбрасывается на новом видео, короткий спуск сверяется с заявленной
  частотой активного декодера, а вердикт «подача вдвое реже» и возврат режима
  действуют только по подтверждённому второму окну и после реальной попытки
  лечения.
* **«Формат HDMI» снова умеет 4:2:2**: список пунктов строится по возможностям
  телевизора (узел `dc_cap`), а не из жёсткого набора «Авто / RGB / YUV 4:4:4»
  из 1.1.0. Демон сверяет правило с этим же узлом и молча пропускает формат,
  которого там нет, поэтому показывать пункт «на всякий случай» нельзя. На
  стендах список вышел «Авто / YUV 4:4:4 / YUV 4:2:2 / RGB»: у ATV14 4:2:2
  заявлен только в 12 битах, у ATV9 — в 8. Глубину демон теперь подбирает по
  EDID: правило задаёт формат, и если у него нет текущей глубины (после смены
  режима система оставила 8 бит), берётся ближайшая заявленная — 4:2:2 станет
  `422,12bit`, а не `422,8bit`, которой у телевизора нет. Явно заданную в
  правиле глубину демон не подменяет: такая комбинация просто не применяется.
  Своё правило от 1.0.x (`… .*=422`) по-прежнему показывается пунктом «Свои
  правила: …» и не затирается. Узел не прочитался — прежний статический набор.
* **Формат больше не пишется в момент смены режима**: запись идёт в точке «режим
  устоялся» — через 2.5 с, после сверки фактической частоты по `vinfo`, и только
  если частота та, что просили. Раньше демон писал формат сразу после транзакции,
  когда узел имени ещё показывал прежний режим; запись переконфигурирует
  HDMI-путь и отменяет сам переход (лог тестера 03.11: все смены 60/50 → 25 Гц с
  записью формата не применились, единственная без записи — применилась; тот же
  эффект виден строкой «таблица режимов SurfaceFlinger сменилась»).
* **Сдача по неприменённому режиму держится до конца видео**: перепроверка замера
  больше не снимает признак «мерить нечего» через ~0.6 с. В логе тестера 03.11
  из-за этого вышло 18 переключений за 6.5 минуты и четыре полных цикла на одном
  канале; теперь на одно видео не больше одного цикла.

* **Неприменённый режим больше не оставляет телевизор без сигнала**: если
  SurfaceFlinger/HDMI не применил запрошенный режим (ядро отдало другую частоту;
  живой случай 02.11 — 25-к/с канал, просили 2160p25, осталось 60 Гц, ТВ показал
  «нет сигнала»), демон подтверждает расхождение повторным чтением `vinfo`,
  повторяет режим через удвоение частоты (25 → 50: у тестера 60 → 25 не
  применялся, а 50 → 25 — применялся) и, если не помогло, оставляет 50 Гц
  (ровнее, чем исходные 60) либо возвращает исходный режим вместе с цветовым
  профилем; до конца видео больше не переключает.

* **Не переключаемся по заведомо неверной заявке плеера**: на ATV11 два разных
  плеера заявили 24 fps на 50-герцовом канале — демон сразу ушёл на 24 Гц, а
  замер через 14 с дал 50, и пользователь видел «двойной перескок».
  Заявленная частота теперь сверяется со счётчиком кадров (окно ~0.7 с): если
  он уже заметно выше заявки, быстрое решение не применяется, и режим меняется
  один раз — по замеру. Сверка двусторонняя и считается после прогрева (1 с от
  первого прироста счётчика — в первую секунду декодер добирает буфер): заявка
  не применяется и тогда, когда счётчик **ниже** неё больше чем на 10 %, поэтому
  «30 fps при реальных 23.976» больше не уводит 50 → 60 Гц. Известное удвоение
  заявки (25 к/с как 50) расхождением не считается: режим от него не меняется.

* **Сеанс AFR «по требованию» по истечении срока возвращал режим** на исходный:
  посреди фильма выходило три переключения подряд (60 → 24 → 60 → 24). Теперь по
  сроку при идущем видео сеанс заканчивается («срок истёк — режим оставляю до
  конца видео»), а возврат остаётся за отменой (`burst 0`), сменой видео и
  настоящей остановкой.

* **Политика дробных частот не применялась к точным источникам** — быстрому
  решению по полю frame rate и подсказке плеера `frame_rate_hint`: при
  «предпочитать дробные» на 23.976 сначала ставились целые 24.00, а через ~15 с
  — 23.98. Теперь политика переводит любое решение (24 → 23.976, 30 → 29.97,
  60 → 59.94; у 25/50 пары нет).

* **Мигание «дробная/целая 24» на вендорном HAL больше не повторяется**: если
  `1080p24hz` нужен в другой дробности, демон пишет `frac_rate_policy` и
  переприменяет тот же режим — а часть прошивок (живой лог тестера ATV11, 07.11)
  возвращает узел к своему значению, то есть переприменение даёт только мигание
  и ничего больше. Теперь отказ HAL запоминается на весь запуск демона: первое
  переприменение — единственное, дальше узел не трогается, и повторяется это
  только после перезапуска демона, а не на каждом ролике (журнал §224).

* **Проба слоя не работала ни у одного плеера**: команда выросла до ~1.24 КБ и
  молча усекалась буфером в 1 КБ — в журнале стояло ложное «слой: статистика не
  получена». Буфер увеличен до 2 КБ, переполнение пишется отдельной строкой.
  Там же исправлен разбор `awk -v exp=…` (порог выбросов считался по периоду
  дисплея): ровный 24p больше не получает «неровная: 84–96 %».

* **Сброс «потолка» приходит по таймеру**, а не на следующем решении: при
  зажатом плеере он задерживался до 16 с (живой замер `.50`: 16 328 мс; после
  правки — 4 879 мс). Куда возвращать режим после подъёма, задаёт новый
  экспертный ключ `switch.restore.bump`: `1` (умолчание) — на максимум, `0` — на
  режим до подъёма (поведение 1.1.0).

* **Обновление с ранних сборок больше не выключает поправку AV1**: устаревшее
  значение `fps.correct.av1=auto` в настройках приложения переносится в «5,7 %»
  и список плееров прежнего встроенного набора (`Av1Migrate`,
  `tests/Av1MigrateTest.java`); в ini `auto` по-прежнему считается выключенным,
  и демон пишет причину в журнал. Раньше после обновления поправка молча
  переставала работать, и 24p в Cobalt снова читался как 25 Гц — режим уходил на
  50. В приложении у «Поправки счётчика AV1» появился готовый пункт «5,7 %».

* **Запрет частот больше не требует угадывать представителя группы**: на
  Android 10/11 и на старом пути «24» и «23.976» — один режим (`1080p24hz`), и
  запрет любой из двух отсекает его целиком (`modes_sel.h`:
  `mode_rate_blacklisted`); в списке настроек больше нет второй, недействующей
  строки. На Android 12–14 оба режима приходят отдельными и запрещаются по
  отдельности: там можно запретить только 23.98.

* **24p больше не уезжает на 50 Гц**: «кратность» считается точно — ошибка
  до 1.2 %, а не 4.3 % (столько между 23.976 и 25). Поэтому 24p без режима 24
  идёт на 60 Гц с распределённым 3:2, а не на 50; то же, когда 24 запрещён в
  `mode.blacklist.rates`.

* **Проба слоя больше не перебивает счётчик, когда тот подтверждён
  заявкой:** на OTT-канале слой отдавал ровно 40.00 мс (25.00 Гц) при счётчике
  23.98 и `frame dur 4004` (23.98) — режим уходил на 50 Гц. Теперь, если
  заявленная длительность кадра того же класса подтверждает счётчик, верим
  счётчику и пин ставим по нему; иначе — слою (случай AV1, где счётчик
  завышает).

* **Проба фактических частот учитывает платформу:** Android 6–9 применяет
  режим записью в `/sys/class/display/mode`, 10–11 — вендорным помощником,
  12–14 — пункт скрыт (режим задаёт SurfaceFlinger, а список уже содержит
  23.98 и 24.00 отдельными режимами). На старых ядрах (4.9) в `vinfo` нет
  поля `frac:` — целость частоты считается по `sync_duration_num/den`.

* **Старый путь: режим больше не «прыгает» 50 ↔ 60 после перемотки.** Сразу
  после пересоздания декодера `vdec_status` отдаёт устаревшее `frame rate 30`,
  а `dump_vdec_chunks`/`dump_vdec_blocks` в это окно пусты — кадры ещё не
  пошли. Вес этого источника набирал порог за 0.8 с, режим уходил на 60 Гц,
  а через секунду дампы давали 25.00 и режим возвращался на 50; следующая
  перемотка повторяла. Теперь `vdec_status` — источник последней надежды: он
  не решает в одиночку, если дампы кэша на боксе работают, а там, где их нет,
  решение по нему принимается не раньше `switch.timeout`. На паузе после
  старта ролика режим больше не залипает на 60 Гц. Живой лог ATV9 (фильм
  25 к/с в Vimu, перемотки) и проверка на `.48`: шесть перемоток подряд —
  режим остаётся 50. Для ролика 30 к/с, где дамп даёт нестандартный сырой
  замер (9 pts за 304 мс = 29.6 Гц), сырой замер сверяется с заявкой
  (допуск 3 %): при согласии заявка принимается в последней попытке, и режим
  уходит 50 → 60; пустой или несогласный дамп заявку по-прежнему не пускает.

* **ATV14: смена таблицы режимов больше не оставляет рабочий стол на частоте
  видео.** Удержание снималось, но режим не возвращался; следующий ролик
  запоминал частоту видео как исходную и возвращал её. Теперь запомненный
  режим возврата (частота и геометрия) ищется в новой таблице и применяется;
  id из старой нумерации не отправляется. Вместе с `switch.restore.preferred`
  рабочий стол получает системный режим.

* **Подъём режима не мигает 59,94 ↔ 60,00 и учитывает политику.** Максимум
  выбирается из доступных режимов с учётом `mode.blacklist.rates` и
  `mode.use.fract` (1 — 59,94, 2 — 60,00); на ATV14 подъём идёт на
  представителя группы, на вендорном пути сравниваются фактические частоты.
  Для 59,94-канала подъёма нет; при политике 2 — один подъём 59,94 → 60,00.

* **«Проверить дробные частоты» действительно скрыт на Android 12–14.**
  Скрытие не срабатывало по двум причинам: путь определялся по числу строк
  `refreshRate=` в дампе SurfaceFlinger (на живых боксах она одна — активный
  режим), а пункт удалялся вызовом `removePreference()` на корневом экране,
  тогда как живёт он во вложенном «Выбор режима». Теперь путь берётся так же,
  как в демоне (`platform_detect`: новый путь Amlogic + Android 12+), а пункт
  убирается у фактической группы. Проверено: `.50` (ATV14) — пункта нет,
  `.48` (ATV9) — на месте.
* **ЧАВО и публикация:** у «Задержка СТОП» пояснено, что на Android 6–9 ноль
  означает «не возвращать режим после видео» (рабочий стол останется на
  частоте ролика); если возврат нужен — 10000–12000 мс.

### Проверено вживую

* Android 14 (Amlogic S905X5M, ядро 5.15): «AFR в OTT включён + OTT в
  `switch.skip.pkg`» — приложение просит 24.69 Гц, режим 25 Гц, подача 24.52 к/с,
  медиана 40.00 мс, 2 % выбросов; «AFR в OTT выключен, частоту ведёт AFRd2» —
  подъём 24→60→50, максимум держался 5347 мс.
* Android 14, переходы каналов (пакет 1.2.0 от 02.11): 1 (1080i50, 50 Гц) -> 210
  (23.976) — 60 -> 24 Гц за ~5 с, а если слой в переходе ещё показывает 25 и
  решает огибающая — за ~21 с; промежуточных 50 нет, установившаяся подача 42 мс,
  0 % выбросов. Обратно 210 -> 1: 60 -> 50 Гц за ~5 с, возврата режима нет.
* Android 9 (UGOOS AM6, ядро 4.9, legacy-путь): 50 Гц → 24 Гц на старте ролика
  23.976 и возврат на 50 Гц после остановки.
* Android 11: режим 50 Гц при включённом AFR в OTT, 0 выбросов.
* Android 9 (UGOOS AM6, legacy): канал 25 к/с — шесть перемоток подряд, режим
  остаётся 50 Гц (`Best src 1 25.00`), ложных 60 нет; локальный 23.976 —
  переключение на 24 Гц по дампам кэша, на перемотках держится.
* Android 14 (`.50`): пункт «Проверить дробные частоты» в «Выборе режима»
  отсутствует; Android 9 (`.48`): пункт на месте с подписью «23.976 / 24».
* Миграция настройки поправки AV1 (`.42`, Android 11, 05.11): в настройках
  выставлено `fps_correct_av1=auto` и пустой список — после запуска приложения
  там `5.7` и три пакета (`io.gh.reisxd.tizentube.cobalt
  com.google.android.youtube.tv com.google.android.youtube`), в ini
  `fps.correct.av1=5.7`, демон пишет «поправка AV1: 5.70 %, только для списка
  плееров».
* «Возвращать цветовой профиль» (пакет 1.2.0 от 02.11): ATV9 (legacy) —
  `запоминаю цветовой профиль 444,8bit`, после остановки `возвращаю цветовой
  профиль 444,8bit`, узел `attr` вернулся к `444,8bit`; ATV14 — чтение и запись
  вендорским клиентом: `запоминаю цветовой профиль 444,12bit`, во время видео
  клиент показывает `422,12bit`, после остановки `444,12bit`.
* Сверка заявки со счётчиком (`.50`, 02.11, сборка с имитацией «плеер заявил
  24 fps» на 50-к/с ролике): `заявлено 24.00 Гц, счётчик даёт 51.88 Гц —
  быстрое решение откладываю, решит замер` → один переход 25 → 50 Гц по замеру,
  без промежуточных 24.
* Неприменённый режим (`.50`, 02.11, сборка с имитацией «ядро отдало не ту
  частоту»): `частота не применилась — перепроверяю через 800 мс` →
  `повторяю режим id 260 через id 257` (25 → 50 → 25) → `целевая частота не
  применилась — оставляю 50.00 Гц (удвоение)`; отдельно проверен возврат
  режима и профиля. Обычный путь 60 → 25 → 50 → возврат прошёл без ложных
  срабатываний.
* «Формат HDMI» на ATV14 и ATV9 (пакет 1.2.0 от 02.11): диалог показывает
  «Авто / YUV 4:4:4 / YUV 4:2:2 / RGB» ровно по `dc_cap`; выбор 4:2:2 пишет
  `2160p[4-9].*=420 .*=422`, демон подставляет заявленную глубину — в журнале
  «формат 422 в текущей глубине не заявлен — беру 422,12bit,full» и
  `Setting color space to 422,12bit,full`; прежнее своё значение от 1.0.x
  остаётся отдельным пунктом.
* Частота по подаче слоя (`.50`, ATV14, 60 Гц, 04.11): 24p в YouTube —
  `слой: p=16.67 a=41.67 n=126 gap=0 — 23.98 Гц`, решение по слою → режим 24 Гц
  (без слоя уходило в 25/50); 25p — слой 40.08 мс, остаётся 50 Гц. Ложных
  переходов на ровном 24p нет: четыре решения подряд с половинами 41.71/41.71.
  Время решения не изменилось (14 с), цена пробы 48 + 54 мс раз в 14–20 с,
  демон 0.1 % CPU.
* Два дефекта владельца (`.50`, 04.11) воспроизведены до правок и закрыты
  после: сеанс `burst` по сроку больше не возвращает режим (живой прогон:
  `срок истёк — режим оставляю до конца видео`, переключений нет; отмена
  `burst 0` и остановка возвращают режим, при `enable=0` демон уходит в пассив),
  а при «предпочитать дробные» быстрое решение сразу даёт 23.98 Гц — второго
  переключения 24.00 → 23.98 нет.
* Не проверено живьём: строка «переход контента» на реальной рекламе — на стенде
  рекламу не показывают, а локальный VFR-файл «30p-реклама + 24p-фильм» играют
  только VLC/Just Player, у которых меток слоя нет. Разбор покрыт host-тестом
  (9 случаев: реклама 30 → 24, смена канала 60 → 24, ровный 3:2, мало меток,
  своя смена режима в буфере).

### Требования и установка

* root (Magisk или встроенный `su` в userdebug-прошивке);
* Amlogic; ядро 5.x — новый путь, ядра 3.14/4.9 — прежний путь AFRd;
* приложение — Android 6.0+ (minSdk 23).

Одновременно должен работать только один экземпляр демона.

* **APK** (интерфейс, настройки, ЧАВО): `ru.reyter.afrd2-1.2.0-release.apk`,
  пакет `ru.reyter.afrd2`. Открыть приложение, дать root и включить автоподбор.
* **Мини-приложение «AFR burst»** (`burstapp-release.apk`, пакет
  `ru.reyter.afrd2.burst`) — необязательное, ставится рядом с APK и служит
  одной кнопкой «сеанс AFR» для мапперов: одна запись в списке приложений, без
  extras и action. Требует установленного AFRd2.
* **Magisk-модуль** (автостарт без приложения): `afrd2-magisk-armeabi-v7a.zip` или
  `afrd2-magisk-arm64-v8a.zip` — Magisk → Модули → «Установить из памяти» →
  перезагрузка. Модуль ничего не пишет в системные разделы.
* **Комплект для ROM-разработчика** (`afrd2-1.2.0-for-rom-dev.zip`): демоны под обе
  ABI, профиль `afrd.ini`, APK и три документа — `integration-rom.md` (встраивание в
  прошивку), `afr-on-demand.md` и `afr-on-demand-answer-to-rom.md`.

Подробности, ограничения и сборка из исходников — в
[README](https://github.com/ReyterAK/afrd2/blob/master/README.md) и
[ЧАВО](https://github.com/ReyterAK/afrd2/blob/master/FAQ-ru.txt).
