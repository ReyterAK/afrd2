**Дата:** 2026-11-03. **Охват:** `afrd.c` (6426 строк, `run_atv14` — 2368 строк), `guard.c`,
`pause.c`, `ceiling.c`, `burst.c`, `colorspace.c`, `hdrinfo.c`, `platform.c`, `sink.c`,

## P1 — искажает поведение

### P1-1. Сдача по неприменённому режиму снимается через 6 с: автоматический цикл 25 ↔ 50

**Исправлено** (`seq.c` + `own_switch_recent (afrd.c:3165)`): сдачу снимает только
`seq_new_video()`, а перезапуск декодера после нашего же применения режима больше не
считается новым видео — признак не зависит от списков зажима. Проверено на `.50` 11:37:
после переключения на 50 Гц в журнале «счётчик кадров сброшен **нашей сменой плотности**»
(раньше — «новое видео»), сдача и `measure_failed` держатся. Replay — `tests/fixtures/seq/tester-25hz.txt`.

`afrd.c:4195` (`own_reset = ceiling_take_restart (cur_sf_id) || …`), `afrd.c:3150`,
`afrd.c:4218-4222`.

«Перезапуск декодера от нашего сброса» распознаётся только если взведён `g_ceiling_us`, а он
ставится в `ceiling_pending_step` — то есть лишь для плееров из `switch.ceiling.pkg` /
`switch.bump.pkg`. У тестера оба списка пусты («потолок: switch.ceiling.pkg пуст — не
сбрасываю», `afrd.log:812`), поэтому `own_reset == false`, и сброс счётчика после **нашего же**
переключения классифицируется как «новое видео» → `retry_gave_up` и `measure_failed` снимаются.

**Доказательство (лог тестера 03.11):** сдача 03:09:15 → «счётчик кадров сброшен — новое видео»
03:09:21 → новое решение 25 Гц 03:10:14 → повторный отказ ядра 03:10:27. Два полных цикла на
одном канале; всего 18 переключений за 6.5 минуты.

**Проверка после правки:** на `.50` правило `.*=422`, `switch.ceiling.pkg=` и `switch.bump.pkg=`
пусты, клип 25 к/с, 3 минуты — в журнале не больше одной строки «счётчик кадров сброшен —
новое видео» на наше же переключение, и не больше одного цикла «повторяю режим».

**Направление:** признак «наш сброс» не должен зависеть от списков: достаточно метки времени
последнего успешного `atv14_apply_mode` (окно 12 с) плюс совпадения `cur_id` с целью.

### P1-2. Формат пишется в момент перехода из блока проверки подачи

**Исправлено**: блок подачи пишет формат только при `mode_verified` (частота текущего
режима подтверждена сверкой), а его таймер перевзводится на повторе. Проверено на `.50`
11:44:12–11:44:16: «Переключаю режим» → «фактическая частота 25.00 Гц» → «Setting color
space». Дополнительно: сверка частоты больше не отменяется перезапуском декодера, вызванным
нашим переключением (см. P1-9).

`afrd.c:4639` (`colorspace_apply_current_mode ()` в блоке `cadence_armed`).

Таймер подачи взводится там же и с тем же сроком (2500 мс), что и проверка частоты, но не
перевзводится при повторе неприменённого режима. Поэтому после повтора (новое применение
режима) первым срабатывает **старый** таймер подачи и пишет формат до сверки фактической
частоты — ровно та запись, которая отменяет переход.

**Доказательство (лог тестера):** повтор 03:07:04.632 → запись `Setting color space to
420,12bit,full` 03:07:06.732 → сверка частоты только 03:07:10.701 (ядро осталось на 50).

**Проверка после правки:** в журнале ATV14 после `Переключаю режим` строка `Setting color
space` никогда не предшествует `фактическая частота дисплея`; в повторе — только после
сверки.

**Направление:** применять формат в блоке подачи только при `vinfo_state == 0 && !hdrinfo_armed`;
при любом новом применении режима перевзводить `cadence_timer`.

### P1-3. Приложение падает от конфига, который демон считает корректным

**Исправлено** (`IniValue`): значение разбирается по правилам демона (комментарий отрезается),
нечисловое значение целого ключа сохраняется строкой. Живая проверка `.50` 11:42: тот же
`switch.timeout=3000 # мс` — приложение открылось, `FATAL EXCEPTION` в logcat нет, экран
настроек доступен. Host-тест `tests/IniValueTest.java`.

`Config.java:208` (`Integer.parseInt (val)` вне try), `cfg_parse.c:74-82` (демон режет строку
по `#`).

Инлайн-комментарий и пустое значение для INT-ключа — норма для демона и падение для GUI:
`switch.timeout=3000 # мс` → `NumberFormatException` из `MainActivity.onCreate` (строка 91 →
`prepareConfig` → `updateConfig` → `conf.load`), приложение не запускается, кнопка сброса
настроек недоступна (она в том же экране).

**Доказательство (живой прогон `.50`, 11:25:22):**
`FATAL EXCEPTION: main … java.lang.NumberFormatException: For input string: "3000 # мс"`.

**Проверка после правки:** тот же ini → приложение открывается, значение показывается как 3000,
демон читает то же самое.

**Направление:** разбирать значение как демон (отрезать `#`), ошибку парсинга превращать в
«оставить как есть + строка в журнале», а не в исключение.

### P1-4. Ручные настройки теряются при обновлении APK

**Исправлено** (`IniMerge`): профиль из ресурсов сливается с текущим файлом — активные ключи
версии главнее, пользовательские сохраняются (комментированная в профиле строка
раскомментируется на месте, без дубля). Живая проверка `.50`: `burst.ms=1500` и
`switch.ceiling.method=codec` пережили `adb install -r`, обе строки ровно по одному разу.
Host-тест `tests/IniMergeTest.java`.

`MainActivity.java:187-240`, `Control.java:200` — ini перезаписывается из `res/raw`
целиком, переживают только ключи из `Config.itemType` (через prefs) и три из `seedOptions`.

Молча теряются задокументированные для ручной правки ключи: `fps.correct.av1.offset/.pct`
(README:284-285), `switch.ceiling.method` (README:274), `switch.revert`, `fps.feed.ratio.pct`,
`fps.feed.gap.pct`, `burst.ms`, `vendor.disp.persist`.

**Проверка:** `switch.ceiling.method=codec` → переустановить APK → `grep ceiling.method afrd.ini`
(пусто); после правки — значение на месте или в журнале сказано, что оно потеряно.

**Направление:** при обновлении не перезаписывать файл, а дополнять отсутствующие ключи;
потерю любого заданного пользователем ключа печатать в журнал.

### P1-5. `pause.mode=keep` перекрывает пользовательский `pause.keep` после первого открытия настроек

**Исправлено**: у пункта «На паузе» появилось значение «Как раньше (по тумблеру ниже)»
(пустая строка, `pause_mode_apply("")` → старые ключи), умолчание строки — пустое.
Живая проверка `.50` после `pm clear`: настройки открыты, в ini нет `pause.mode` вовсе,
`pause.keep=1` в силе.

`preferences.xml` (`pause_mode`, `android:defaultValue="keep"`), `SettingsFragment.java:24-28`,
`afrd.c:3626-3638`.

Новая строка сохраняет XML-умолчание при первом показе. У пользователя 1.1.0, где `pause_keep`
на новом пути действовал, значение «возвращать сразу» молча заменяется на «держать».

**Проверка:** prefs `pause_keep=false` → открыть/закрыть настройки → запустить приложение →
в журнале `пауза: pause.mode=keep`; после правки — поведение прежнее либо строка о миграции.

**Направление:** не сеять умолчание, пока ключ не задан явно; при миграции переносить
`pause.keep` в `pause.mode` один раз и сообщать об этом.

### P1-6. Сеанс AFR «по требованию» не заканчивается по стопу и паузе

**Исправлено**: конец видео (стоп, конец ролика, пауза сверх предела) выставляет
`g_burst_video_ended`, и сеанс закрывается с причиной «видео кончилось». Живая проверка
`.50`: сеанс `burst 60000` → стоп плеера → `сеанс AFR: конец (видео кончилось), возвращаю
режим` (12:12:14.565), в сеансе ни одного лишнего переключения.

`afrd.c:3982-3990` (конец сеанса — только срок/отмена/смена потока),
`afrd.c:4381-4404` (`PAUSE_END`/`PAUSE_RESUME`), `docs/afr-on-demand.md:112-113` («строго одно
переключение»).

Стоп видео и пауза дольше `switch.delay.off` сеанс не завершают; `PAUSE_END` + `PAUSE_RESUME`
дают ещё два переключения (при `pause.mode=off` — на каждой паузе).

**Проверка:** `.50`, burst + `pause.mode=off`: посчитать `Переключаю режим` за сеанс (ожидание —
одно) и строку `сеанс AFR: конец`.

**Направление:** завершать сеанс по `video_eff == false` и по `PAUSE_END`, как и обещано.

### P1-7. Отказ транзакции на ATV14 повторяется каждые ~300 мс

**Исправлено**: ветка `apply_rc == -2` больше не привязана к вендорному пути — цель
снимается, `measure_failed` и `seq_give_up` выставляются, строка одна («backdoor не применил
режим»). Живьём не воспроизводилось: для этого нужно сломать backdoor на стенде; проверено
чтением кода и совпадением с поведением вендорного пути (§116).

`afrd.c:5627` — разбор `apply_rc == -2` закрыт условием `sink == SINK_VENDOR_MODE`.

На основном пути (`SINK_SF_1035`) при отказе `atv14_apply_mode` цель остаётся в `want_sf_id`,
`measure_failed` не ставится, и `guard_decide` возвращает `SWITCH` каждую итерацию: поток
`fork/exec` и строк «backdoor не применил режим id N».

**Проверка:** отозвать backdoor-помощник на `.50`, за минуту посчитать строки и транзакции
(после правки — одна попытка на видео).

**Направление:** обрабатывать `-2` одинаково на обоих путях (снять цель, поставить
`measure_failed`, сообщить один раз).

### P1-8. «До конца видео не переключаем» обходится подсказкой плеера и «режим не найден»

**Исправлено**: подсказка плеера проверяет `seq_allows_switch()`, «режим для X Гц не найден»
и неудачное быстрое решение вызывают `seq_give_up()` — тот же признак, что и повтор.
Проверяется `tests/test_seq.c` (переключение запрещено после сдачи, новое видео снимает
запрет).

`afrd.c:5404-5437` (подсказка ставит `want_sf_id`, снимает `measure_failed`, но не снимает
`retry_gave_up`), `afrd.c:5376-5390` («режим для X Гц не найден» ставит `measure_failed`, но не
`retry_gave_up`).

В обоих случаях перепроверка замера возвращает замер, и цикл повторяется — то есть сдача,
введённая в `8eb8eb3`, держится не во всех путях.

**Проверка:** плеер с `frame_rate_hint` после сдачи (например, IPTV с заявленной частотой):
после правки — ни одного `Переключаю режим` до конца видео.

**Направление:** любое «больше не пробую» ставить одним флагом в одном месте.

### P1-9. Сверка частоты иногда не выполняется вовсе

**Исправлено**: короткий провал декодера (перезапуск после нашего же переключения) больше не
снимает ни таймер сверки, ни сдачу — `blip = hdrinfo_armed && own_switch_recent (cur_sf_id)`.
Живая проверка `.50` 11:59.691 → 12:02.873: сверка есть, формат поставлен после неё. Случай с
провалом внутри 2.5 с в этом прогоне не повторился — остаётся проверить на боксе тестера
(пять переключений подряд, у каждого сверка в пределах 3.5 с).

`afrd.c` ветка `!video_eff` (~4450) и обработка «счётчик кадров сброшен» (~4280).

Живой прогон `.50` 11:45: переключение 11:45:24.952 (50 Гц) — строки «фактическая частота»
нет вовсе, через 2.9 с пришёл сброс счётчика («нашей сменой плотности»). На следующем
переключении (11:45:43.375) сверка выполнилась нормально. Правка `if (!own_reset)` закрывает
путь сброса счётчика, но не ветку «видео кончилось»: короткий провал декодера при перезапуске
снимает `hdrinfo_armed`, и «приняло ли ядро режим» остаётся непроверенным — ровно тот случай,
ради которого сверка вводилась (в логе тестера такие переключения тоже без сверки).

**Проверка:** `.50`, 5 переключений подряд на 25-к/с канале: у каждого «Переключаю режим»
должна быть строка «фактическая частота» в пределах 3.5 с.

## P3 — документация и мёртвый код

- README-таблица ключей: нет 7 ключей (`switch.revert`, `switch.bump.probe.ms`,
  `switch.ceiling.pkg`, `fps.feed.ratio.pct`, `fps.feed.gap.pct`, `vendor.disp.persist`,
  `uevent.filter.hdcp`); таблица путей повторяет ошибки P2-9/P2-10.
- `cfgkeys.c:63-67`: комментарий «`switch.ceiling.pkg` следует за `switch.bump.pkg`» —
  ветка недостижима (`afrd.c:6320-6345`).
- `CsPolicy`: мёртвые `NONE/AUTO/RGB/YUV444`, `indexOf(String)`, `valueAt()`; комментарий
  называет умолчанием YUV444, хотя умолчание — «Авто».
- `preferences.xml`: мёртвая строка `pause_keep`, 12 неиспользуемых строк ресурсов,
  подпись «Держать 20 с» при фактическом пределе из `switch.delay.off`.
- `afrd.c:3796/3822/3867`: умолчания демона расходятся с профилем (recheck 8000 против 4000,
  envelope.early 0 против 14000, `fps.correct.enable` 0 против «включён»).
- `afrd.c:2347`, `2470`, `5603`: комментарий про снятие `g_video_rate_floor` не соответствует
