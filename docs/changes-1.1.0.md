# AFRd2 1.1.0 — изменения относительно 1.0.0

Дата выпуска: 27 октября 2026. Заявка прежняя: Android 11–14 (Amlogic); старый путь
(Android 6–9) не изменён.

## «Зажим» частоты

Плеер (замерено на штатном YouTube TV) запоминает частоту дисплея в начале сессии
проигрывания и внешнюю смену режима не перечитывает: ролик, начатый под 50 Гц, после
подъёма до 60 продолжал отдавать ~50 к/с, и картинка оставалась задёрганной до
перезапуска ролика (замер по подаче видео-слоя: 49.4 против 59.94 к/с).

Теперь демон:

* поднимает режим до максимума, поддержанного ТВ, ещё до первого кадра плеера
  (`switch.bump`), в том числе сразу по исчезновению канала декодера при смене ролика
  и по выходу плеера на передний план (`switch.bump.on.app`) — это закрывает и
  холодный старт, где декодер появляется позже, чем плеер запоминает частоту;
* если переключение всё же пришлось на живое видео, сбрасывает «потолок» частоты
  (`switch.ceiling.reset`): перезапуском процесса кодека, а при его отказе — сменой
  плотности экрана. Плеер перечитывает режим, и подача выправляется с текущей позиции
  ролика. Сброс делается один раз на видео, отложенно и только если целевой режим выше
  того, под которым началось видео.

Живые замеры: ATV14 — 50.34 → 59.94 к/с, провал подачи 83 мс; Android 11 — 50.02 →
59.94 к/с за 0.26 с с сохранением позиции ролика.

Новый способ сброса (`switch.ceiling.method`):

* `auto` (умолчание) — перезапуск процесса кодека, при отказе — смена плотности;
* `codec` — только перезапуск кодека;
* `density` — только смена плотности (прежнее поведение).

Перезапуск кодека пересоздаёт только сессию декодера: на ATV14 декодер пропадает на
68 мс и возвращается на 1.1 с (смена плотности стоит 6.8 с и перезапускает Activity).
Имя сервиса ищется опросом init (Codec2 на Android 12+, OMX на 8–11), поэтому способ
годится и для Android 10/11, где плотность стоила 1.5–2.5 с. Цена: перезапускается HAL,
то есть декодер у всех приложений сразу (фоновое воспроизведение в другом приложении
прервётся).

## Кому применяются механики зажима

* Список `switch.bump.pkg` (по умолчанию — только штатный YouTube): зажим измерен
  именно у него, у остальных плееров он не подтверждён, а запасной способ сброса
  (смена плотности) — это смена конфигурации экрана, на которой часть плееров
  перезапускает Activity (OTT Navigator при первом срабатывании AFR возвращался к
  предыдущему каналу вместо текущего). Пустой список выключает механики совсем —
  остаётся обычный замер и переключение по нему.
* Плеер из списка «Плееры, которым AFR мешает» (`switch.skip.pkg`) механики не
  получает в любом случае: этот список обещает не трогать режим вообще.
* В приложении новые пункты «Устранять зажим частоты» (один тумблер на обе механики)
  и «Плееры, которым устранять зажим».

## Умолчания для Android 11–14

* `switch.skip.pkg` теперь пуст на всех путях: штатный YouTube больше не исключается
  из автоподбора. На Android 10/11 прежнее исключение опиралось на оценку «сброс
  потолка стоит 1.5–2.5 с», которая живым замером не подтвердилась (реально 0.26 с).
  Обновление переносит настройку само: из списка убирается только штатный YouTube,
  свои записи сохраняются.
* `switch.ceiling.reset` включён по умолчанию на обоих путях: его умолчание следует
  за `switch.bump`, но сам сброс от подъёма не зависит и при выключенном подъёме
  остаётся единственной защитой от зажима.
* Способ по умолчанию — перезапуск кодека (`switch.ceiling.method=auto`): он не меняет
  режим экрана, поэтому зажим снимается без лишнего переключения и с сохранением
  позиции ролика.

## Android 10/11

* Постоянный помощник смены режима (`vendor.disp.persist`) держит виртуальную машину и
  классы HIDL загруженными: смена занимает 0.34–1.09 с вместо 0.85–1.76 с (раньше
  каждая смена запускала отдельный `app_process`, ~490 мс из этого времени). Любой
  отказ — откат на прежний разовый запуск; ключ можно выключить без потери работы.

## Прочее

* Относительная поправка на завышение AV1-счётчика (`fps.correct.av1.pct`): завышение
  пропорционально частоте (23.976 → 25.40, 59.94 → 63.30), прежняя аддитивная поправка
  его не лечила. По умолчанию выключена.
* Приложение находит рабочий `su` на стоковых прошивках: на userdebug-сборках Amlogic
  в PATH первым стоит старый AOSP-su, не понимающий `-c`, а Magisk держит свой в
  `/debug_ramdisk/su`. Раньше приложение сообщало «требуется root», хотя root был.
* «Запрещённые частоты развёртки» (`mode.blacklist.rates`) задаются выбором из частот,
  которые поддерживает ТВ, а не строкой с числами: 23.976 и 24 — разные записи.
* «Формат HDMI (цветовое пространство)» (`cs.select`) — выбор из трёх пунктов вместо
  строки с регулярными выражениями; правило защиты полосы 4K сохранено в каждом.
* Демон перечитывает текущий режим экрана перед решением о переключении: раньше он
  доверял кэшу, а режим мог сменить кто-то другой (штатная АПЧ Amlogic, плеер со своим
  автоподбором), и 60-фпс ролик оставался на 25 Гц.
* Исправлено падение приложения при запуске на спящем боксе (Android 8–9): служба
  стартует через `startForegroundService`, отказ не роняет приложение, запуск
  повторяется при получении фокуса окна.
* Журнал: «HDMI not active» печатается только на реальном событии HDMI, а не при
  намеренной перезагрузке конфига.
* Документация: калибровка поправки частоты (`tools/stand/fps_calib.sh`), разведка
  незнакомого бокса (`tools/stand/recon_box.sh`), замер времени переключения телевизора
  (`tools/stand/tv_switch_lat.sh`), документ для встраивания в прошивку.
