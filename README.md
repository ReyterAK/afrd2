Auto Frame Rate Daemon (AFRD)
-----------------------------

AFRd2: Android 10–14 и Android TV 14 (ядро 5.x, Amlogic S905X5M)
----------------------------------------------------------------

Этот репозиторий — форк [AFRd](https://github.com/anpaza/afrd) (upstream 0.3.2).
Форк аддитивный: путь для Android 6–9 (ядра 3.14/4.9) сохранён без изменений, а
для Android 10–14 добавлен рабочий — там декодер больше не рассылает uevent'ы, а
запись в `/sys/class/display/mode` режим не переключает. Нужная ветка выбирается
на старте автоматически (`platform_detect()`): новая ветка включается, если есть
`/sys/class/vdec/vdec_status` **и нет** старых узлов `/sys/class/switch/hdmi/*`
(так живые Android 6–9 остаются на своём штатном пути). Наличие backdoor
SurfaceFlinger проверяется отдельно — пробным вызовом транзакции 1035: без него
ветка всё равно выбирается, но демон уходит в пассивный режим, AFR не работает и в
лог пишется предупреждение.

Что делает новая ветка:

* следит за декодером, опрашивая `/sys/class/vdec/vdec_status` (`device name` —
  признак видео, рост `frame count` — что видео не на паузе);
* определяет частоту по приросту `frame count`; заявленные `frame rate`/`frame dur`
  из того же узла на ядрах 5.x бывают мусором (на синтетических клипах драйвер
  рапортует 30 fps при реальных 23.976), поэтому `frame dur` применяется только
  как уточнение рядом с замером — см. `fps.declared.crosscheck.pct` ниже.
  Если есть — приоритетнее подсказка плеера через API (`fps.prefer.api`);
* переключает режим backdoor-транзакцией SurfaceFlinger
  (`service call SurfaceFlinger 1035 i32 <modeId>`), поэтому SurfaceFlinger и HDMI
  остаются синхронными;
* возвращает исходный режим на остановке видео и снимает флаг backdoor (также по
  `SIGTERM`/`SIGINT`, на старте демона и по таймауту «видео потеряно»);
* сохраняет API UDP 50505: `frame_rate_hint`, `status`, `help` и `reconf` работают
  как раньше, а `refresh_rate` на ATV14 не поддержан — демон пишет в лог «refresh_rate
  в ATV14 не поддержан» и режим не меняет (см. «Ограничения»). `reconf` перезагружает
  конфиг без перезапуска процесса: режим возвращается, флаг backdoor снимается, файл
  перечитывается.

### Сборка

Нужен NDK (проверен r26d):

```sh
NDK=$HOME/Android/Sdk/android-ndk-r26d ./mka          # оба ABI
AFRD_ABIS=armeabi-v7a ./mka                           # только бинарник для бокса
```

Результат для бокса — `libs/armeabi-v7a/afrd` (ELF 32-bit ARM, API 21,
зависимости только libc/libm/libdl). `./mka` без аргументов дополнительно
раскладывает бинарники и профили в `android/app/src/main/res/raw/` (для сборки
APK) и правит `versionName` в `android/app/build.gradle`.

### Установка и запуск

Демону нужен root (чтение sysfs и backdoor SurfaceFlinger). Установка — вариант B,
как в оригинале: бинарник кладётся на устройство и запускается под root;
автозапуск появится вместе с приложением (отдельный этап).

```sh
D=192.168.88.50:5555
adb connect $D
adb -s $D root        # если прошивка разрешает adb root; иначе выполняйте команды через su
D=$D sh tools/stand/build_push.sh
```

`build_push.sh` делает всё сразу: снимает прошлый экземпляр демона, копирует
`libs/armeabi-v7a/afrd` → `/data/local/tmp/afrd` и `config/afrd2.ini` →
`/data/local/tmp/afrd.ini`, делает бинарник исполняемым, запускает
`/data/local/tmp/afrd -v -D /data/local/tmp/afrd.ini` и печатает pid с хвостом лога.

Те же шаги вручную:

```sh
adb -s $D push libs/armeabi-v7a/afrd /data/local/tmp/afrd
adb -s $D push config/afrd2.ini /data/local/tmp/afrd.ini
adb -s $D shell chmod 755 /data/local/tmp/afrd
adb -s $D shell '/data/local/tmp/afrd -D /data/local/tmp/afrd.ini'
```

Полезное:

```sh
adb -s $D shell 'pidof afrd'                                          # демон жив?
adb -s $D shell 'tail -20 /data/local/afrd.log'                       # лог (log.file; прошлый — afrd.log~)
adb -s $D shell '/data/local/tmp/afrd -k'                             # остановить (pid-файл /dev/run/afrd.pid)
adb -s $D shell '/data/local/tmp/afrd -k -D /data/local/tmp/afrd.ini' # перезапуск (нужен после правки конфига)
adb -s $D shell '/data/local/tmp/afrd -s'                             # статистика (shmem /dev/run/afrd.ipc)
# toybox nc с -u на этой прошивке не завершается после ответа — под timeout (124 — норма):
adb -s $D shell 'echo status | timeout 2 nc -u -w1 127.0.0.1 50505'   # статус через API
```

### Профиль config/afrd2.ini

Ключи, которые использует новая ветка (полный список — в самом файле):

| ключ | смысл |
|---|---|
| `enable` | включить демон |
| `log.file`, `log.enable` | файл лога (по умолчанию `/data/local/afrd.log`) |
| `trigger.poll.ms` | период опроса `vdec_status` |
| `trigger.start.debounce.ms`, `trigger.stop.debounce.ms` | дебаунс старта/стопа видео |
| `fps.measure.envelope.ms`, `fps.measure.envelope.max.ms`, `fps.measure.envelope.sub.ms`, `fps.measure.envelope.skip.ms`, `fps.measure.retries` | наблюдение перед решением (20 с), предел расширения (30 с), длина подокна (5 с), прогрев (2 с) и число попыток; частота берётся по **нижней огибающей** подокон, а не по одному окну |
| `fps.declared.crosscheck.pct` | допуск уточнения замера заявленной длительностью кадра (`frame dur`), %; `0` — выключить |
| `fps.recheck.delay.ms` | через сколько мс после переключения перемерить частоту и поправить режим, если класс другой (0 — выключить) |
| `fps.prefer.api` | предпочитать подсказку плеера (`frame_rate_hint`) собственному замеру |
| `switch.timeout` | страховочный таймаут, мс (по умолчанию 3000): если `vdec_status` не читается дольше него, а режим ещё удержан — удержание снимается, чтобы флаг backdoor не залип |
| `switch.restore.on.stop` | возвращать исходный режим при остановке видео |
| `switch.skip.pkg` | плееры, которым AFR мешает («пакет», список через пробел): демон их мерит и пишет в журнал, но режим не переключает и не удерживает (по умолчанию `com.google.android.youtube.tv`, см. ограничение 8); действует на обоих путях — Android 6–14, но на Android 6–9 такой плеер не измеряется: гейт стоит до запуска измерения, в журнале только сам факт исключения |
| `mode.min.hz.list` | минимальная частота режима для конкретных плееров («пакет=Гц»): ниже неё режимы не выбираются. Если для частоты контента есть ровное кратное выше порога — берётся оно (25 → 50), иначе самый быстрый доступный режим (24 → 60). Действует на обоих путях — Android 6–14; на Android 6–9 порог только отсеивает режимы ниже него, остальное — прежнее правило выбора, а если подходящего не осталось — обычный выбор без порога (в журнале: «нет режима не ниже ... Гц (mode.min.hz.list)»). Значение задаётся в приложении: строка «Минимальная частота режима для плееров» — плеер выбирается отметкой в списке, частота вводится в той же строке. Закомментированный пример в профиле — подсказка для ручной правки: приложение отражает значение ключа в свои настройки, поэтому после первого запуска в конфиге остаётся активная строка (пустая, если настройка не задана); непустое значение, прописанное в профиле, при старте переносится в настройки и дальше хранится там, поэтому оно переживает обновление APK (профиль из ресурсов перезаписывается, настройки — нет). Демон хранит не больше восьми записей: если в значении их больше, приложение обрезает лишние и сообщает об этом. Имя пакета применяется целиком до 255 символов (буферы демона — `PKG_NAME_LEN` в `pkgdet.h`); более длинное приложение не даст добавить |
| `pause.keep` | 1 — на паузе режим удерживать (по умолчанию), 0 — возвращать исходный |
| `fps.correct.enable`, `fps.correct.list` | калибровка поправок: мастер-выключатель (по умолчанию **включён** — работает поправка AV1 ниже) и список поправок по плеерам (по умолчанию пуст) |
| `fps.correct.av1.offset`, `fps.correct.av1.pkg` | аддитивная поправка на завышение счётчика AV1-трактом декодера (кадр/с; по умолчанию **`0.1`**, `0` — выключено) и ограничение по пакету плеера (пакет выбирается тем же экраном приложений, что и `switch.skip.pkg`, но в режиме одиночного выбора); действует только при `fps.correct.enable=1` |
| `fps.measure.window.ms`, `fps.measure.window.max.ms` | **устарели** (решение по огибающей): известны, но не действуют, в логе — «устарел: заменён fps.measure.envelope.ms (Android 10-14)» |

Все ключи, которые демон знает, перечислены в `cfgkeys.c` вместе с указанием, на каком
пути они действуют. Ключ, который на текущем пути не действует (или вообще неизвестен —
опечатка), **называется в логе при старте**, а не игнорируется молча:

| ключ | ATV14 (Android 10-14) | legacy (Android 6-9) |
|---|---|---|
| `enable`, `log.file`, `log.enable`, `mode.prefer.exact`, `mode.use.fract`, `mode.blacklist.rates`, `switch.timeout`, `switch.skip.pkg`, `mode.min.hz.list`, `cs.select`, `cs.list.path`, `cs.path` | действует | действует |
| `trigger.poll.ms`, `trigger.start.debounce.ms`, `trigger.stop.debounce.ms`, `fps.*`, `pause.keep`, `switch.restore.on.stop` | действует | — |
| `mode.extra`, `mode.path`, `vdec.sysfs`, `vdec.blacklist`, `frhint.vdec.blacklist`, `hdmi.sysfs`, `hdmi.state`, `switch.delay.on/off/retry`, `switch.blackout`, `switch.ignore`, `switch.hdmi`, `uevent.filter.*` | — (в логе: «не действует на новом пути») | действует |
| `toast.hz` | — (настройка приложения, демон её не читает) | — |

Пути sysfs на новой ветке определяются автодетектом (`platform_detect()`), а не конфигом.
В GUI приложения настройки, недействующие на ATV14, показаны **неактивными** с пометкой
«(не действует на Android 10-14)», а недействующие на Android 6–9 (`fps.correct.*`) —
с пометкой «(не действует на Android 6-9)» — чтобы настройка не выглядела работающей.

Списки пакетов в GUI (`switch.skip.pkg`, `fps.correct.av1.pkg`) задаются не вводом
текста, а выбором из отдельного экрана приложений: по умолчанию показаны только плееры
(флаг «Только плееры», снимается — список всех приложений), уже выбранные пакеты видны
всегда, даже если не проходят по фильтру. `switch.skip.pkg` набирается несколькими
отметками, `fps.correct.av1.pkg` — режимом одиночного выбора (метка снимается повторным
нажатием, пустое значение — «для любого плеера»).

Ключ `mode.prefer.exact` на новом пути **читается**: при `0` (значение ATV14-профиля)
для 25-фпс контента выбирается 50 Гц, для 30-фпс — 60 Гц (кадры дублируются 2:1, картинка
плавнее на большинстве ТВ); при `1` берётся точная частота (25/30 Гц). Правила те же, что
в legacy-ветке: допускаются кратные частоты с ошибкой до 4.3 % и кратностью не выше 3.
Когда режим выбран как кратный, в лог пишется строка вида
«режим 50.00 Гц выбран как кратный (x2) для 25.00 Гц».

Ключ `mode.blacklist.rates` на новом пути тоже **читается**: частота из списка не выбирается
ни в каком разрешении (например, `mode.blacklist.rates=50` уводит 25-фпс контент на 25 Гц).

Ключ `mode.use.fract` на новом пути **читается**: `1` — внутри группы частот выбирается
дробный представитель (23.976 / 29.97 / 59.94), `0` — точный (24.000 / 30.000 / 60.000).
По умолчанию в ATV14-профиле стоит `1`: счётчик кадров пару 0.1 % не различает, а контент
почти всегда идёт с дробной частотой (плёнка 23.976, NTSC 29.97/59.94); так же ведёт себя
legacy-путь при `mode.use.fract=1`. Если ТВ не поддерживает дробный режим, resolver берёт
ближайший из таблицы SurfaceFlinger (допуск 0.125 Гц — 23.976 и 24.000 отличаются на
0.024 Гц), то есть точный, без ошибки.

Ключ `fps.recheck.delay.ms` (в профиле 4000) задаёт **перепроверку замера**: через это
время после переключения демон наблюдает частоту ещё раз (свой горизонт огибающей) и меняет
режим, только если класс однозначно другой (один раз на видео). Нужен потому, что у некоторых
плееров первый участок смещён набором буфера (VLC: 60-фпс канал давал 47.9–50.3 fps → режим
50 Гц, после перепроверки — 60.6 fps → `1080p60hz`). Знание о конкретном плеере не требуется —
только счётчик кадров. `0` — выключить перепроверку.

Нижняя огибающая (ключи `fps.measure.envelope.*`) — основной механизм устойчивости. На ATV14
счётчик кадров завышен **односторонне**: плеер повторно декодирует кадры на границах
DASH/HLS-сегментов, AV1-тракт декодера добавляет свои, но ничто кадры не отнимает. Поэтому
частота берётся как **минимум** из частот подокон длиной `fps.measure.envelope.sub.ms` (5 с):
короткие всплески и повторные кадры поднимают отдельные подокна, но не опускают все. Подокна
начинаются не раньше `fps.measure.envelope.skip.ms` (2 с, прогрев: первый участок бывает
занижен), горизонт наблюдения — `fps.measure.envelope.ms` (20 с); при неоднозначном
доверительном интервале он расширяется до `fps.measure.envelope.max.ms` (30 с). Пауза и
буферизация **сбрасывают наблюдение целиком**: счётчик кадров стоит, прежние выборки к
текущему наблюдению не относятся, и после возобновления отсчёт `skip.ms + envelope.ms`
идёт заново (а не просто выбрасывается одно «грязное» подокно). Сброс счётчика (новое видео)
делает то же самое.

**Цена:** режим переключается не раньше чем через `skip.ms + envelope.ms` ≈ 22 с после старта
видео (было 1.5–6 с). Для файлов и потоков это незаметно; видео короче горизонта просто не
переключается (режим остаётся прежним). `envelope.ms=0` фактически поднимается до
`skip.ms + sub.ms` — раньше этого подокна решения быть не может, то есть «переключать сразу»
быстрее одного подокна всё равно не выйдет. В логе решению предшествует строка
`видео: <HZ> Гц по огибающей (N с наблюдения, горизонт M мс), ищу режим`.

**Точность (измерено 2026-10-01, 13 роликов YouTube):** решение по одному окну угадывало
24-фпс ролики в 14 % случаев, минимум по скользящим 5-с подокнам за 20 с — в **86 %**;
25-фпс ролики определяются верно в **100 %** случаев. Ошибки — только в сторону 25 Гц
(24-фпс ролик уходит в 25/50 Гц; пропуск кадра заметнее повтора).

Поправки `fps.correct.*` — по умолчанию **включена** кодековая поправка AV1 со значением **`0.1`**
(список поправок по плеерам пуст). Значение подобрано по живым записям (13 роликов YouTube; считалась
та же статистика, что применяет демон — нижняя огибающая по 5-с подокнам), критерий — правило
владельца «ошибка 24→25 лучше ошибки 25→24» (визуальный A/B 2026-10-02):

| смещение | 24 fps верно | 25 fps верно | 25→24 (запретных) |
|---|---|---|---|
| 0 | 5/7 | 6/6 | 0 |
| **0.1** | **6/7** | **6/6** | **0** |
| 0.2 | 6/7 | 6/6 | 0 |
| 0.3 | 6/7 | 5/6 | 1 |
| 0.5 | 7/7 | 4/6 | 2 |
| 1.0 | 7/7 | 3/6 | 3 |

`0.1`–`0.2` — единственная зона, где 25-фпс остаются 100 %, а 24-фпс угадываются на один ролик
лучше, чем без поправки; выбран `0.1` — тот же результат при вдвое большем запасе до запретной
стороны (ближайший 25-фпс ролик стоит на 0.28 fps выше границы класса).
**Гарантии «100 %» нет ни у какого значения:** на контрольной выборке из 65 роликов два честных
25-фпс ролика измерились ниже границы класса **вообще без поправки** (огибающая смещена вниз), а
разброс внутри одного воспроизведения доходит до ±0.5 fps. Более точный источник частоты —
заявленный `frame dur` — на AV1 бесполезен: драйвер всегда отдаёт 3200 (30 fps).

* `fps.correct.enable` / `fps.correct.list` — калибровка по плееру (относительная, в
  процентах): `fps.correct.list=com.google.android.youtube.tv=5.0` означает «замер этого
  плеера делить на 1.05»; положительное значение — плеер завышает частоту. Как измерить:
  включить лог, дать видео 30–60 с, найти в логе строку `плеер <пакет>: поправка замера
  ±P % (fps.correct.list)` (видно, какой пакет распознан) и строку `видео: X Гц по огибающей
  (N с наблюдения, горизонт M мс), ищу режим`, сравнить с номиналом (для YouTube —
  `yt-dlp -F <url>`, колонка FPS).
* `fps.correct.av1.offset` / `fps.correct.av1.pkg` — **аддитивная поправка AV1** (кадр/с).
  Измерено на одном и том же файле Sintel 24.000 fps в Just Player: H.264 — 24.002 fps,
  AV1 — 24.520 fps, то есть AV1-тракт декодера завышает счётчик на **+0.5 кадра/с**;
  штатный клиент YouTube добавляет к этому своё. `fps.correct.av1.pkg` ограничивает поправку
  одним пакетом (пусто — любой плеер). **Условий применения два:** `fps.correct.enable=1` **и**
  поле `device name` из `vdec_status` содержит `av1` — на H.264/VP9-тракте поправка не
  применяется и строка в лог не пишется. Значение по умолчанию `0.3` (включено): огибающая
  уже снимает большую часть завышения, а поправка «переусиливает» честный 25-фпс контент — с
  ней 25-фпс ролики уходили в 24 Гц (верно 50–67 % вместо 100 %). На «пограничном» 24-фпс
  ролике YouTube поправка класса не меняет даже при `offset=0.5`: доверительный интервал
  после неё пересекает границу, решение берётся по следующему решаемому окну. Огибающая уже
  снимает типовое завышение, поэтому поправка — ручной инструмент; включать, только если у
  конкретного плеера смещение больше ~1 кадра/с и огибающей не хватает.
  **Рекомендуемое значение — `0.3`, а не `0.5`** (решение владельца 2026-10-01): ошибка
  «24 fps определён как 25 Гц» предпочтительнее обратной, поэтому поправка не должна уводить
  честный 25-фпс контент в 24 Гц. На 13 живых AV1-роликах YouTube `offset=0.3` исправляет один
  24-фпс ролик и не портит ни одного 25-фпс; `offset=0.5` в живой серии увёл честный 25-фпс ролик
  (`z7do1hhb6fE`) в `1080p24hz` (журнал §16.7).

**Решение владельца (2026-10-01):** калибровка по плееру (`fps.correct.list`) остаётся
выключенной — завышение на YouTube непостоянно (24-фпс ролик +5.5 %, 25-фпс — +1.7 %), и одна
поправка на пакет выбирает, какой из соседних классов считать верным. Огибающая решает ту же
задачу без знания о плеере; кодековая поправка AV1 **включена со значением `0.1`** — это наибольшее
значение, при котором на живой выборке ни один 25-фпс ролик не уходит в 24 Гц, а 24-фпс угадываются
на один ролик лучше, чем без поправки (см. таблицу выше); `0.5` из документации убрано как
нерекомендованное.

**Важно:** завышение +5 % — свойство **штатного приложения YouTube** (AV1-путь). На SmartTube
(`org.smarttube.stable`, VP9) счётчик точен: 24-фпс ролик измерялся 23.966–23.975 (24.03 fps за 20 с при
номинале 23.976), 25-фпс → класс 25 + удвоение, режимы выбираются правильно **без калибровки**. То есть
при использовании SmartTube правильный AFR для 24-фпс контента YouTube работает и с выключенной
`fps.correct.*`. Стартовое занижение у SmartTube, как и у VLC, отсекается прогревочным
подокном огибающей (`fps.measure.envelope.skip.ms`), а перепроверка `fps.recheck.delay.ms`
остаётся страховкой.

### Как убедиться, что AFR работает

```sh
sh tools/stand/check_mode.sh     # другой бокс: D=<ip:port> sh tools/stand/check_mode.sh
```

печатает одну строку: `kernel mode | HDMI: sname, h_freq, v_freq | SF activeMode | backdoor flag`.
Частоты берутся из одной строки `disp_mode` — `h/v_freq: <h>/<v>`, где `h` в Гц, а
`v` в мГц (для 1080p59.94 это `67433/59940`); нечитаемое поле печатается как `n/a`.

Если проиграть клип 23.976 fps в VLC (у него нет своего AFR), фактическая картина
(живой прогон 2026-09-29 22:08/22:27, см. «Статус приёмки»):

* до старта: `1080p60hz | sname: 1080p60hz, 67433, 59940 | activeMode=59.94 Hz | debugDisplayModeSetByBackdoor=false`
* во время: `1080p24hz | sname: 1080p24hz, 26973, 23976 | activeMode=23.98 Hz | debugDisplayModeSetByBackdoor=true`
* после остановки: снова `1080p60hz` и `debugDisplayModeSetByBackdoor=false`

Матрица приёмки и дополнительные проверки:

```sh
sh tools/stand/acceptance_matrix.sh                        # 23.976/25/50: удержание и возврат
PAUSE_TEST=1 sh tools/stand/acceptance_matrix.sh           # + пауза (PAUSE_EXPECT=restore для pause.keep=0)
OWN_AFR_TEST=1 sh tools/stand/acceptance_matrix.sh         # + плеер со своим AFR
API_TEST=1 sh tools/stand/acceptance_matrix.sh             # + API, подсказка плеера, сброс счётчика (R34в)
LOG=acceptance.log sh tools/stand/acceptance_matrix.sh     # + протокол в файл
sh tools/stand/guard_test.sh                               # SIGTERM: режим возвращён, флаг снят
```

Клипы ожидаются в `/sdcard/Download/afr/` (23.976/24/25/50/60 fps). Скрипты сами
печатают `ls -l` этого каталога и пропускают отсутствующие клипы как `SKIP`, а не
выдают их за пройденные. Полезные переменные: `D` (адрес устройства),
`CLIPS`/`CLIP_DIR` (что играть), `ORIG_MODE` (куда обязан вернуться демон,
по умолчанию `1080p60hz`).

Коды возврата матрицы: 0 — все проверки OK, 1 — есть FAIL, 2 — проверить не удалось
(стенд недоступен, демон не запущен, одни SKIP). Матрица требует запущенного демона:
без него она выходит с кодом 2 и ничего не «доизмеряет».

процент, решение уточняется ею — 24.766 fps превращается в 23.976, и режим становится

### Приёмка 2026-10-02: выбор канала `vdec_status` (R61) и стенд «гладко/дёргано»

**R61 — выбор канала декодера.** `vdec_status` печатает блок на каждый зарегистрированный
инстанс. Раньше парсер брал первый блок; залипший (zombie) инстанс с замороженным счётчиком
ослеплял демон (в наблюдении 02.10 висел 19 ч и пережил остановку всех плееров) — AFR молча не
работал до перезагрузки или `setprop ctl.restart android-hardware-media-c2-hal-1-2`. Теперь
разбираются все каналы, активный выбирается по растущему счётчику (из растущих — самый свежий;
при паузе — последний, самый свежий инстанс).

Проверено: хостовые наборы (двухканальная фикстура + выбор канала, сценарии «залипший первым»,
«пауза», «новое видео», «канал исчез», «растут оба»), полная NDK-сборка и `make MODE=debug` —
без предупреждений; живой регресс обычного пути (23.976 → `1080p24hz` + `sync_duration_num=23976`,
стоп → `1080p60hz`, флаг backdoor снят). **Не проверено вживую:** сам залипший канал —
воспроизведением он не форсируется (появлялся спонтанно), поэтому сценарий покрыт только
фикстурой, повторяющей реальный формат двух блоков.

**Стенд «гладко/дёргано» (`tools/stand/stutter_probe.sh`).** Разбирает жалобу «один и тот же
ролик то гладкий, то дёрганый»: снимает раз в секунду режим/частоту/счётчики каналов, дампы
`dumpsys SurfaceFlinger --latency` видео-слоя до и после переключения, вендорские события
FRA/HWC (`frameRateDisplay`, `adjustVsyncMode`) и печатает вердикт по ровности подачи кадра
(интервалы `actualPresentTime` относительно среднего; норма для 24 Гц — чередование 2/3 периода
60-Гц сетки ≈33/50 мс). Вердикт по прогону не заменяет глаз владельца: он нужен, чтобы
**поймать и оцифровать именно плохой прогон**.

Наблюдение в этот день: событие вендорского FRA `frameRateDisplay 1,… → adjustVsyncMode to
MixMode` (HWC входит в «видео»-режим vsync) в обычных прогонах присутствует; в единственном
«подозрительном» прогоне 02.10 оно отсутствовало (HWC остался в `HwMode`) — совпадение или
причина дёрганья **не доказано**, решается визуальной приёмкой. Рычагов прямого вызова FRA нет:
`vendor.amlogic.hardware.systemcontrol@1.1` — HIDL-сервис (hwbinder, не виден в `service list`),
а вендорский CLI для него инертен (`meson_display_client -F` → `ret:1`).

**Сторож флага backdoor (R57) — сделан и проверен живьём.** Приложение следит за
признаком жизни демона в общей памяти (heartbeat меняет CRC-штамп каждый цикл) и
перезапускает его при застое ~12 с; демон на старте снимает залипший флаг.
`kill -9` при удержанном режиме → перезапуск за ≤14 с, флаг снят
(`tools/stand/watchdog_test.sh`). Заодно исправлено переизвлечение демона из APK
(по времени установки, а не по неизменному `versionName`) — иначе обновлённый APK
оставлял в кэше старый бинарник.

**Дёрганье — что показал объективный замер (`stutter_probe.sh`).** Метрика
«удержаний» (интервалы подачи слоя > 1.35×среднего) на живом стенде даёт:

| контент | режим 23.98 Гц | режим 50 Гц | режим 59.94 Гц |
|---|---|---|---|
| AV1 4K 24 fps | **0 удержаний** | 10–11 | 0 (шаблон 3:2) |
| H.264 24 fps | **0 удержаний** | 10 | 0 (шаблон 3:2) |

То есть дёрганье определяется **нецелым отношением** частоты контента к частоте
дисплея (24 на 50 Гц даёт кратные трём удержания), а не кодеком. Выборы самого
демона (23.98 для 24 fps, 50 для 25/50 fps, 59.94 для 60 fps) в устойчивом
режиме дают 0 удержаний. Дёрганым может быть окно **до** решения демона (до ~22 с
для 24/25 fps), когда режим уже сменил плеер со своим AFR или вендорский FRA —
демон вмешивается только после замера. Аномалия «HWC не вошёл в MixMode» (§19.4)
на 17 прогонах батча не воспроизвелась, и она объясняла бы лишь лёгкое подёргивание;
настоящая «катастрофа» — другая и найдена ниже.

**«Катастрофа» с картинкой («как 10 fps») — найдена, воспроизведена и лечится.**
Симптом владельца: тот же ролик, поведение демона одинаковое, а картинка иногда идёт рывками,
будто видео 10–13 fps. Воспроизведено на стенде: если **переключить режим при живом видео**, в
~40 % случаев (5 из 12) подача видео-слоя становится **вдвое реже периода дисплея** (при 24 Гц —
интервалы ~72 мс вместо 41.7 мс) при `HWC` в `MixMode` и `DEVICE`-композиции. Механизм: смена
режима не пересчитывает vsync-путь HWC (`adjustVsyncMode` на транзакцию 1035 не вызывается), и
кадры систематически «не успевают» к обновлению. Подбор вариантов на воспроизведении: повторная
выдача того же режима **не лечит** (77 мс), а смена режима «туда-обратно» (возврат → целевой)
**лечит** (41.7 мс). Демон теперь сразу после переключения проверяет интервалы подачи
(`fps.cadence.fix.ms`, по умолчанию 2500 мс) и при «половинной подаче» делает «туда-обратно»
(до 2 раз на видео). Проверка на серии: 6 прогонов штатного YouTube (4K AV1) с демоном — все
ровные (41.71 мс, 0 удержаний).

**Раннее решение (меньше ожидания перед первым переключением).** Пока не набрано всё
наблюдение (`fps.measure.envelope.ms`, 20 с), демон режим не трогал — по одному 5-с подокну 24-фпс
контент определяется верно лишь в ~14 % случаев. Теперь при согласии двух разнесённых подокон
(один класс, скорости в пределах 1.5 %) решение принимается на `fps.measure.envelope.early.ms`
(профиль: 14000; меньше «прогрев + 2 подокна + 1 с» не бывает). Живой замер: локальный клип
23.976 — переключение через ~16.5 с вместо ~21 с.

### Ограничения (осознанные, а не баги)

1. **Цветовое пространство применяется, HDR — нет.** На ATV14-пути sysfs-узел
   `attr` пишется с ошибкой, поэтому значение применяется вендорским сервисом
   (`/vendor/bin/meson_display_client -s "HDMI Color ATTR" <значение>`), а правила
   `cs.select` сопоставляются с именем режима; по умолчанию правило одно —
   `2160p[4-9].*=420` (4K и ≥40 Гц требуют 420 по полосе HDMI), остальные режимы
   не трогаются, чтобы не спорить с выбором системы. Применение повторяется через
   ~2.5 с после переключения: фреймворк переустанавливает цвет асинхронно и
   перебивает значение, выставленное «в момент» смены режима (проверено живьём).
   **HDR/Dolby Vision демон не трогает** — ими управляют система и плеер.
   Для диагностики демон **читает** атрибуты дисплея у того же вендорского
   сервиса (`-r dumpDisplayAttribute`): HDR Mode, HDR Policy, HDR Priority,
   SDR Mode, FORCE HDR Mode. Они пишутся в журнал (при `-v`: при старте — на
   любом пути Android 10-14, и через ~2.5 с после переключения режима, когда
   система уже выставила свои значения) и отдаются в ответе API `status`
   (`hdr mode:` и т. д.; `-1` — если вендорского клиента нет, то есть на пути
   Android 6-9).
2. **HDCP не управляется.** Узлов `/sys/module/hdmitx20/...` на ядрах 5.x нет,
   HDCP-ветка upstream здесь не работает (тоже тема отдельного этапа).
   Проверено живьём (02.10, ATV14-бокс): включить HDCP из оболочки нельзя —
   запись в `/sys/class/amhdmitx/amhdmitx0/hdcp_mode` (`on`, `1`, `14`, `22`)
   принимается (`rc=0`), но узел остаётся `off`, службы `hdcp_tx22`/`vendor.tee_hdcp`
   не поднимаются; вендорская команда переподтверждения на этой прошивке не
   реализована (`raw cmd userSpaceHDCPTxAuth is not supported now`). Смена режима
   (та же транзакция 1035, что у демона) HDCP тоже не включает. То есть HDCP здесь
   поднимается только путём защищённого воспроизведения (DRM), и переподтверждать
   его после смены режима демону не требуется для обычного контента.
   Инструмент для снятия состояния — `tools/stand/hdcp_probe.sh`.
3. **`refresh_rate` через API не действует; `color_space` — действует.** `refresh_rate`
   на ATV14-пути не поддержан (в лог пишется «refresh_rate в ATV14 не поддержан»), а
   `color_space` переопределяет цвета до следующего переключения режима (сбрасывается
   перезагрузкой конфига) и применяется тем же путём, что и правила `cs.select` — на ATV14
   через вендорский сервис (см. выше). **`reconf` работает:** демон
   возвращает исходный режим, снимает флаг backdoor, перечитывает `afrd.ini` и
   продолжает работу без перезапуска процесса — как правкой файла, так и командой
   API `reconf`.
4. **Нужен backdoor SurfaceFlinger.** Если прошивка его не поддерживает (другой
   вендор, будущие версии Android), демон пишет в лог «backdoor SurfaceFlinger
   недоступен — пассивный режим» и AFR не работает.
5. **Внезапная смерть демона оставляет флаг backdoor поднятым — теперь
   лечится сторожем.** Проверено живьём (`kill -9`): режим остаётся прежним,
   а `debugDisplayModeSetByBackdoor` — `true`, и приложения со своим AFR
   перестают переключать режим. Приложение (вариант B) следит за признаком
   жизни демона в общей памяти (heartbeat меняет CRC-штамп каждый цикл) и при
   застое ~12 с перезапускает демон, а тот на старте снимает залипший флаг
   (`tools/stand/watchdog_test.sh`: перезапуск за ≤14 с). Сторож работает по
   shmem, а не по pid-файлу: на ATV14 `/proc` смонтирован с
   `hidepid=invisible` и процессов root приложению не видно. Альтернатива без
   приложения — Magisk-модуль с циклом перезапуска. Перезагрузка бокса тоже
   лечит (SurfaceFlinger стартует с чистым флагом).
6. **Меняется только частота.** Разрешение не трогается (режим ищется для текущего
   разрешения), экран на время переключения не гасится — дешёвого способа на ATV14
   нет, экран моргает как при обычной смене режима.
7. **Только Amlogic.** На не-AmLogic устройствах и на Android < 10 работает
   upstream-ветка (как раньше).
8. **Некоторым плеерам AFR мешает — для них режим не переключается
   (`switch.skip.pkg`).** Проверено живьём (2026-10-02, штатный YouTube TV): плеер
   выбирает темп отрисовки в момент **старта ролика** по текущему режиму экрана
   (min(частота ролика, частота экрана)) и потом его не пересматривает — ролик,
   стартовавший под низким режимом, остаётся зажатым (30 fps под 24 Гц играл
   24.2 к/с; 60 fps под 50 Гц — 50.3 к/с; пауза/воспроизведение и переключение
   режима «туда-обратно» не помогают, помогает только переоткрытие ролика).
   Именно это ломало основной сценарий — **листание роликов**: удержанный от
   предыдущего ролика режим (например, 50 Гц для 25-фпс контента) зажимал
   следующий. Единственная политика без зажима вообще — не переключать режим для
   такого плеера, поэтому по умолчанию `switch.skip.pkg=com.google.android.youtube.tv`:
   демон мерит частоту и пишет всё в журнал, но режим не трогает. **На Android 6–9:**
   плеер из списка там не измеряется — гейт стоит до запуска измерения, в журнале
   только факт исключения. Экран остаётся
   на режиме системы (обычно 60 Гц) — он не ниже частоты любого контента, зажим
   невозможен; 24/25/30/60 fps плеер раскладывает сам по сетке 60 Гц (30 и 60 —
   идеально, 24 — распределённое 3:2, 25 — мягкая неравномерность). **Оговорка:**
   для такого плеера режим задаёт сама система, поэтому её режим должен быть не
   ниже частоты контента (обычно 60 Гц). Если ТВ в EDID предпочитает 50 Гц (как
   проверенная панель), а среди роликов бывают 60-фпс, задайте режим явно:
   `cmd display set-user-preferred-display-mode 1920 1080 60` — иначе система сама
   выберет 50 Гц, и 60-фпс ролик снова окажется «зажатым». Следствие:
   для этого плеера не действуют `pause.keep` и `switch.restore.on.stop`
   (удерживать нечего) и экран не мигает. Для плееров, которые «зажимают» темп,
   но которых всё же стоит переключать, остаётся `mode.min.hz.list` («пакет=Гц»,
   ниже неё режимы не выбираются). Когда плеер подаёт кадры реже ожидаемого,
   демон пишет в журнал строкой «подача неровная: X мс при периоде Y мс, ожидание
   Z мс» (порог 1.125×) — проверка работает и для пропущенных пакетов, и это
   отличает такой случай от дисплейной «половинной подачи» (ровно вдвое), которую
   демон лечит сам. На Android 6–9 оба списка работают так же; пакет приложения
   на переднем плане там определяется общим разбором дампа `dumpsys activity`
   (кэш 2 с, запрос выполняется только когда список непуст), но плеер из
   `switch.skip.pkg` там не измеряется: гейт стоит до запуска измерения, в
   журнале — только факт исключения.

Ниже — описание upstream (Android 6–9), оно сохранено как есть.

This is a Linux daemon for AMLogic SoC based boxes to switch screen
framerate to most suitable during video play. The daemon uses kernel
uevent-based notifications, available in AMLogic 3.14 kernels from
summer 2017. Earlier kernels won't emit notifications at the start
and end of playing video, so the daemon won't work.

Unfortunately, this uevent is gone from kernel 4.9 (used for
Android 7 and 8), so afrd can't use frame rate notifications
on newer kernels. Instead, afrd will use video decoder notifications
that are emitted at the start and end of playback.

The daemon can be linked either with BioniC (for Android) or with
glibc (for plain Linux OSes).

Versions up to 0.1.* use kernel uevent notifications emmited by
AMLogic kernels starting from summer 2017, used in some Android 6.0
and 7.0 firmwares. Unfortunately, somewhere around start of 2018
AMLogic broke its own code and since then these uevents are not
generated (altough part of the respective code is still in kernel).
Here are a example FRAME_RATE_HINT uevent generated when a 29.976
fps movie is started:
```
change@/devices/virtual/tv/tv
    ACTION=change
    DEVPATH=/devices/virtual/tv/tv
    SUBSYSTEM=tv
    FRAME_RATE_HINT=3203
    MAJOR=254
    MINOR=0
    DEVNAME=tv
    SEQNUM=2787
```
and when the movie stops:
```
change@/devices/virtual/tv/tv
    ACTION=change
    DEVPATH=/devices/virtual/tv/tv
    SUBSYSTEM=tv
    FRAME_RATE_END_HINT
    MAJOR=254
    MINOR=0
    DEVNAME=tv
    SEQNUM=2788
```
Since version 0.2.0 afrd supports detecting movie framerate by
catching uevent's generated when a hardware decoder is started
or stopped. These events are present on both older and newer
kernels, thus afrd can work with almost every AMLogic kernel
out there:
```
add@/devices/vdec.25/amvdec_h264.0
    ACTION=add
    DEVPATH=/devices/vdec.25/amvdec_h264.0
    SUBSYSTEM=platform
    MODALIAS=platform:amvdec_h264
    SEQNUM=2786

remove@/devices/vdec.25/amvdec_h264.0
    ACTION=remove
    DEVPATH=/devices/vdec.25/amvdec_h264.0
    SUBSYSTEM=platform
    MODALIAS=platform:amvdec_h264
    SEQNUM=2789
```
These events do not contain the movie frame rate, thus in addition
to these events afrd has to query the video decoder driver, its status
is available from /sys/class/vdec/vdec_status:
```
vdec channel 0 statistics:
  device name : amvdec_h264
  frame width : 1920
 frame height : 1080
   frame rate : 24 fps
     bit rate : 856 kbps
       status : 63
    frame dur : 4000
   frame data : 19 KB
  frame count : 230
   drop count : 0
fra err count : 0
 hw err count : 0
   total data : 1197 KB
```
The "frame dur" field is used if not 0 (the actual frame rate is
96000/frame_dur), and "frame rate" field is used otherwise
(with 23 fps being 23.976, 29 being 29.970 and 59 being 59.94 fps).

Configuration file
------------------

AFRD uses a simple configuration file that can be used to customize
its behavior. The file contains either comment lines, starting with
the '#' character, or key=value pairs.

If a key contains several values, list elements are always separated
by white spaces.

Every 5 seconds afrd will check the last-modified timestamp on the
loaded config file. If config file is changed, afrd reloads it.

The following parameters are recognized by AFRD:

* *hdmi.dev*
    This keyword defines the sysfs directory with HDMI driver attributes.
    Usually has the value /sys/class/amhdmitx/amhdmitx0.

* *hdmi.state*
    This defines the sysfs file used to check if HDMI is enabled or not.
    Usually has the value /sys/class/switch/hdmi/state.

* *switch.delay.on*
* *switch.delay.off*
    The time to delay a mode switch when video starts (on) or stops (off).
    The 'on' delay is usually small, while 'off' should be relatively big
    to avoid unneeded mode switches at position change or when you're
    watching a series of videos with same framerate.

    Setting a parameter to zero will disable the respective operation.
    For example, if you want to completely disable restoration of the
    original refresh rate, set switch.delay.off to 0.

    The time is given in milliseconds.

* *switch.delay.retry*
    Sometimes video decoder doesn't report movie frame rate correctly.
    In these cases afrd will wait some time and try the query again.
    This keyword defines the time interval between these tries.

    The time is given in milliseconds.

* *switch.timeout*
    If movie frame rate cannot be safely determined for this period
    of time, afrd will give up trying.

* *switch.blackout*
    When movie starts after this period of time the screen will be
    disabled to minimize flicker. Don't set it too low as in some
    circumstances screen may be blackened when it shouldn't be.

* *switch.ignore*
    If time interval between a STOP/PLAY operation is less than given
    amount of milliseconds, afrd will not re-evaluate movie fps. This
    is useful to avoid suddent refresh rate switches due to wrong fps
    evaluation during movie rewind operations.

* *switch.hdmi*
    Number of milliseconds to delay HDMI hot-plug event handling.
    When HDMI is plugged out, afrd will clear the list of supported
    video modes, and when it is plugged in, afrd will query the list
    of supported modes (which is retrieved from TV EDID data), but it
    has to wait a little so that things settle down (till kernel driver
    does its job).

    Some strange TVs will simulate a HDMI off/on event pair on every
    refresh rate switch, this can be seen in afrd log. In this case
    this parameter should be either 0 (which means to ignore HDMI
    hotplug events), or larger than the "HDMI off" period.

* *mode.path*
    Points to sysfs file used to switch current video mode.
    This is usually /sys/class/display/mode.

* *mode.prefer.exact*
    If set is 1, AFRD will prefer exact match of video mode refresh rate
    to movie frame rate. If 0 (default setting), AFRD will prefer the
    video mode with highest refresh rate which is a exact multiple of
    movie frame rate.

    Default value is 0.

* *mode.use.fract*
    Choose how AFRD handles fractional frame rates (23.976, 29.97, 59.94 fps):

    * 0 - Use both fractional and integer refresh rates as appropiate
    * 1 - Prefer fractional refresh rates, even if movie says it uses integer
    * 2 - Prefer integer refresh rates, even if movie says it uses fractional

    This can be used to limit the number of mode switches, e.g. when your OS
    is set up to use 59.94Hz refresh rate (the default on AndroidTV boxes with
    Android 8+) to avoid a mode switch when watching 30 or 60Hz videos
    you can set this to 1.

* *mode.blacklist.rates*
    This option allows you to blacklist some refresh rates. For example,
    AMLogic kernels have a bug in the HDMI driver that sets the 29.976 mode
    wrong; using this refresh mode causes severe jittering on 23.976 movies.
    Thus, this refresh rate is blacklisted by default.

    This is a list of numbers separated by spaces.

* *mode.extra*
    Normally afrd takes the list of supported video modes from EDID info blob
    fetched via HDMI from your TV. Sometimes this info doesn't contain all the
    supported modes. You can put a list of additional supported video modes
    that aren't listed

* *vdec.sysfs*
    This points to sysfs directory containing the status of the video decoder.
    afrd will try to use attributes vdec_status, dump_vdec_blocks, dump_vdec_chunks.

* *uevent.filter.frhint*
* *uevent.filter.vdec*
* *uevent.filter.hdmi*
    These sets the filters for kernel uevents we handle:
    * *frhint* for the FRAMERATE_HINT uevent generated on some older and patched
        kernels when video decoder detects a change of framerate in played video
    * *vdec* for uevents generated by the video decoder when a hardware decoder
        is activated or deactivated
    * *hdmi* for uevents generated when we plug in or out the HDMI connector.

    Event filters use the following format:

    uevent.filter.XXX=&lt;keyword&gt;=&lt;regex&gt;[ &lt;keyword&gt;=&lt;regex&gt;...]

    The regular expressions are "extended regular expressions" and are matched
    against the whole attribute value. E.g. regular expression "plat" will not
    match the string "platform", while "platform" or "plat.*" will.

    Regular expressions cannot contain space characters, which are used to
    delimit attribute filters from each other. If you need a space, use the
    [[:space:]] regular expression.

* *frhint.vdec.blacklist*
    A list of video decoders to ignore FRAME_RATE_HINT events from. For example,
    the amvdec_h265 codec will always report 26 fps on every video in a
    FRAME_RATE_HINT event. By ignoring this FRAME_RATE_HINT event you give
    a chance to afrd to use other sources to determine the correct frame rate.


AFRd API
--------

AFRd has an API which can be used to cooperate with video player software in order
to get a better user experience. In particular, software may tell afrd in advance
what is the frame rate of the video, so that afrd doesn't have to guess it.

The API is available by sending UDP datagrams to address 127.0.0.1, port 50505.
The protocol is purely textual, each datagram may contain multiple commands,
each command on a separate line.

The format of each line is:

	<command> [<arguments> ...]

The following commands are available:

* *help*
    display a list of supported commands and their short description

* *frame_rate_hint* <fr>
    tell afrd the video starting in less than one second will use
    <fr>/1000 frames per second (e.g. 23976 = 23.976 fps).

* *refresh_rate* <rr>
    tell afrd to set display refresh rate as close to <rr>/1000 Hz
    as possible immediately, no arg to restore original rate.

* *color_space* <cs>
    override colorspace, empty arg to restore default behavior.
    The <cs> specificator may contain, separated by comma:
    * The color space itself (one of rgb, 444, 422, 420)
    * The color depth (8bit, 10bit, 12bit, 16bit)
    * The color range (limit or full)
    Color space takes effect on next refresh rate switch.

* *status*
    get current afrd status

* *reconf*
    tell afrd to reload configuration file as soon as possible

To test the API you may use the 'nc' tool that is part of busybox, which can be
easily installed if you didn't already. Example dialog with afrd, lines starting
with '>' are outgoing, others are incoming:

```
1|u211:/ # nc -u 127.0.0.1 50505
>help
frame_rate_hint <fr>
	tell afrd the video starting in <1.0 seconds will use <fr>/1000 frames per second (e.g. 23976 = 23.976 fps)
refresh_rate <rr>
	tell afrd to set display refresh rate as close to <rr>/1000 Hz as possible, no arg to restore original rate
color_space <cs>
	override colorspace, empty arg tor restore default behavior
status
	get current afrd status
reconf
	tell afrd to reload configuration file as soon as possible

>status
enabled:1
active:0
blackened:0
version:0.2.5
build:2019-03-31 21:17:38
current hz:50000
original hz:50000

>refresh_rate 59940

>status
enabled:1
active:1
blackened:0
version:0.2.5
build:2019-03-31 21:17:38
current hz:59941
original hz:50000

>refresh_rate

>status
enabled:1
active:0
blackened:0
version:0.2.5
build:2019-03-31 21:17:38
current hz:50000
original hz:50000

>color_space rgb,8bit,full
>refresh_rate 50000
```

Note how afrd remembers original refresh rate when you switch it for the first time,
and how it restores refresh rate when the command 'refresh_rate' without parameters
is issued.
