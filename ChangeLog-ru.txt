0.3.2 (форк afrd2, ветка afrd2-atv14) Птн Окт 02 10:20:00 МСК 2026

    Сторож флага backdoor (R57): демон больше не оставляет режим «залипшим»
    после своей внезапной смерти.

    * демон пишет в общую память признак жизни (heartbeat), который растёт на
      каждой итерации цикла; приложение (вариант B) считает демон мёртвым,
      если CRC-штамп не менялся 4 опроса подряд (~12 с), и перезапускает его,
      а демон на старте снимает залипший флаг backdoor. Живой тест:
      `kill -9` при удержанном режиме → демон поднялся сам за ≤14 с, флаг снят
      (`tools/stand/watchdog_test.sh`);
    * почему не по pid-файлу: на ATV14 `/proc` смонтирован с `hidepid=invisible`,
      приложению не видно процессов root — проверка `/proc/<pid>/cmdline`
      всегда давала ENOENT, а сторож по ней зацикливал перезапуски. Heartbeat
      виден через ту же общую память, что и статистика, и не требует root;
    * приложение переизвлекает демон и профиль из ресурсов по времени установки
      APK (`PackageInfo.lastUpdateTime`), а не по `versionName`: форк держит
      versionName неизменным, из-за чего после обновления APK в кэше приложения
      оставался старый бинарник демона (найдено живьём 02.10: крутился демон
      сборки 30.09 без R61).

0.3.2 (форк afrd2, ветка afrd2-atv14) Чтв Окт 01 12:00:00 МСК 2026

    Решение о частоте на ATV14-пути - по нижней огибающей вместо окна замера;
    добавлена аддитивная поправка AV1 (включена по умолчанию, 0.3 кадра/с).

    * счётчик кадров vdec_status завышен односторонне: плеер повторно декодирует
      кадры на границах DASH/HLS-сегментов, AV1-тракт декодера добавляет свои,
      но ничто кадры не отнимает. Поэтому частота берётся как минимум из частот
      подокон длиной fps.measure.envelope.sub.ms (5 с), начиная не раньше
      fps.measure.envelope.skip.ms (2 с, прогрев). Горизонт наблюдения -
      fps.measure.envelope.ms (20 с); при неоднозначном доверительном интервале
      он расширяется до fps.measure.envelope.max.ms (30 с). Пауза и
      буферизация сбрасывают наблюдение целиком: после возобновления отсчёт
      skip.ms + envelope.ms идёт заново (прежние выборки не используются), а не
      просто выбрасывается одно "грязное" подокно; сброс счётчика (новое видео)

      5-с подокнам за 20 с - в 86 %, для 25-фпс - 100 %; ошибки только в сторону
      25 Гц (пропуск кадра заметнее повтора);
    * латентность первого переключения выросла до skip.ms + envelope.ms (в
      профиле ~22 с); видео короче горизонта режим не переключает. Ключи прежнего
      окна fps.measure.window.ms / fps.measure.window.max.ms устарели: остаются
      известными, демон пишет в лог "устарел: заменён fps.measure.envelope.ms
      (Android 10-14)";
    * новая опциональная поправка AV1 (fps.correct.av1.offset, fps.correct.av1.pkg):
      аддитивная, в кадрах/с, на завышение счётчика AV1-трактом декодера
      (измерено на одном файле Sintel 24.000 fps: H.264 - 24.002, AV1 - 24.520,
      то есть +0.5 кадра/с). Выключена по умолчанию (offset=0) и действует только
      при fps.correct.enable=1 и только если поле "device name" содержит av1;
      pkg ограничивает поправку одним плеером (пусто - любым);
    * приложение (android/): в раздел "Настройки для Android 10 и выше" добавлены
      пункты огибающей (наблюдение, предел, подокно, прогрев), в раздел калибровки
      по плееру - пункты поправки AV1 (с оговоркой, что она действует только при
      включённой калибровке); пункты устаревшего окна замера убраны, чтобы
      приложение не писало в ini недействующие ключи.

0.3.2 (форк afrd2, ветка afrd2-atv14) Втр Сен 29 21:45:00 МСК 2026

    Порт на Android 10-14 (Android TV 14, ядро 5.x, Amlogic S905X5M).
    На новых ядрах декодер не рассылает uevent'ы, а запись в
    /sys/class/display/mode режим не переключает, поэтому добавлен
    отдельный путь. Старый путь (Android 6-9) не изменён: реализация
    выбирается на старте автоматически (platform_detect).

    Новый путь:

    * триггер - опрос /sys/class/vdec/vdec_status (признак видео - поле
      "device name" и рост "frame count");
    * частота кадров - по приросту "frame count" (поля frame rate и
      frame dur на этих ядрах недостоверны), при наличии - по подсказке
      плеера через API (fps.prefer.api); окно замера fps.measure.window.ms
      расширяется шагом window.ms/3 до fps.measure.window.max.ms, пока
      доверительный интервал (+-1 кадр счётчика и +-неопределённость меток
      времени) не уложится в одну группу частот; внутри групп 23.976/24,
      29.97/30, 59.94/60 выбирается дробный представитель (как
      frac_rate_policy на legacy-ветке). Без этого один "лишний" кадр за
      окно 1.5 с (2.8%) переводил 23.976/24 в 25 Гц: граница классификации
      24 -> 25 лежит на 24.49 fps, то есть ближе одного кадра. Пауза или
      остановка счётчика не тратит попытку замера и не выключает AFR до
      конца файла; enable=0 действительно выключает переключение;
    * уточнение замера заявленной длительностью кадра: если поле frame dur из
      vdec_status отличается от замера не более чем на fps.declared.crosscheck.pct
      (по умолчанию 5%), решение берётся по заявленной частоте. Так лечится
      систематическое завышение счётчика на IPTV: плеер повторно декодирует
      кадры на границах HLS-сегментов (канал 23.976 fps измерялся как
      24.56-24.77, +2.4-3.3%, и уходил в 25 Гц). Далёкие значения игнорируются:
      на синтетических клипах драйвер рапортует "30 fps" при реальных 23.976;
    * frame_rate_hint применяется и когда режим уже удержан — смена эпизода или
      канала в том же плеере раньше оставляла прежний режим;
    * mode.use.fract на новом пути читается: 1 - дробные режимы (23.976/29.97/59.94,
      значение по умолчанию в профиле ATV14), 0 - точные (24.000/30.000/60.000);
      если ТВ не поддерживает дробный режим, resolver берёт ближайший из таблицы;
    * fps.recheck.delay.ms (по умолчанию 8000) - перепроверка замера через N мс
      после переключения: режим меняется, только если класс однозначно другой.
      Лечит смещённое первое окно у некоторых плееров (60-фпс канал давал 47.9-50.3
      fps и уходил в 50 Гц; после перепроверки 60.6 fps -> 1080p60hz). Знание о
      конкретном плеере не требуется;
    * приложение (android/): распознаёт ATV14 (ядро 5.x + /sys/class/vdec/vdec_status)
      и отдаёт профиль afrd_atv14.ini; зависимость eu.chainfire:libsuperuser
      заменена собственной RootShell, репозиторий jcenter - на mavenCentral
      (jcenter закрыт, без этого APK не собирается);
    * переключение режима - backdoor-транзакция SurfaceFlinger 1035
      (service call SurfaceFlinger 1035 i32 <modeId>), поэтому
      SurfaceFlinger и HDMI остаются синхронными;
    * возврат исходного режима на остановке видео (switch.restore.on.stop),
      снятие флага backdoor на стопе, по SIGTERM/SIGINT, на старте демона
      и по таймауту "видео потеряно";
    * пауза настраивается (pause.keep): 1 (по умолчанию) - режим на паузе
      удерживается, 0 - возвращается исходный;
    * API UDP 50505 работает: frame_rate_hint, status, help; refresh_rate в

0.2.2 Птн Мар 8 00:34:39 2019 +0300

    Существенно улучшено распознавание частоты кадров запущенного видео.
      * После старта видео afrd выжидает 300мс.
      * Через каждые 100мс вычисляется fps по данным из
        /sys/class/vdec/dump_vdec_blocks (если они есть)
      * Параллельно вычитывается fps из /sys/class/vdec/vdec_status
      * Если три раза подряд показания этих двух параметров совпали
        с точностью 0.1%, afrd считает, что это истиный fps видео.
