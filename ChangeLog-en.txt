1.2.0 Sun Nov 1 2026
    Release after 1.1.0: AFR on demand (a session triggered by a button), a real
    "auto" fractional rate policy, a check of the actual display rate; settings
    without duplicates (AV1 correction and pause behaviour are one item each,
    items that do not apply on the current path are hidden); mode restoration on
    stop no longer leaves the launcher at the video rate.

    * Clamp fixes: OTT Navigator is excluded from AFRd by default on
      Android 10+ (switch.skip.pkg) — it manages the rate itself through
      Surface.setFrameRate (live check: 50 -> 24 Hz in ~8 s, feed 50.00 fps,
      0 outliers), and the daemon's bump/revert only fights it. On Android 6-9
      AFRd2 works as usual: the player has its own AFR there, but the default
      exclusion applies to the new path only.
      The default switch.bump.pkg is the stock YouTube; the ceiling reset
      (switch.ceiling.reset) has its own switch.ceiling.pkg list, YouTube only.
      New key switch.revert: if the feed stays clamped after a switch and the
      "there and back" treatment does not help, the mode is returned to the
      previous one (22 % -> 0 % outliers, at the cost of dropping part of the
      content frames). The feed check counts the share of outlier intervals
      (fps.feed.ratio.pct / fps.feed.gap.pct) instead of relying on the median
      alone, so a ragged feed no longer reports "feed is fine".

    * Fixed (live check on ATV14, 02.11): a decision that matches the mode
      already on screen no longer stops measuring until the end of the video
      (a 1080i50 channel could stay at 60 Hz); "frame counter is not growing"
      no longer fires on a new channel from the previous video's timer; the
      short descent after bump does not trust the layer feed when it disagrees
      with the decoder's declared rate. Switching from channel 1 (1080i50,
      50 Hz) to 210 (23.976): 60 -> 24 Hz in ~5 s, no intermediate 50/60.
      The feed verdict acts only on a confirmed second window, and the mode
      revert only after a real treatment attempt: a false "feed does not heal"
      on 1080i50 no longer flickers the mode.

    * "About": the "Testers" field is back (as in the original AFRd) —
      Acorn@4PDA, SlimHouse@4PDA.

    * "HDMI format" (cs.select) supports YUV 4:2:2 and 4:2:0 again: the list
      of items is built from what the TV reports (the dc_cap node) instead of
      the fixed "Auto / RGB / YUV 4:4:4" set of 1.1.0. The daemon checks a
      rule against the same node and silently skips a format missing there,
      so an item "just in case" cannot be shown. On ATV14 and ATV9 the list
      became "Auto / YUV 4:4:4 / YUV 4:2:2 / RGB" (ATV14 reports 4:2:2 in
      12-bit only, ATV9 in 8-bit); picking 4:2:2 writes
      "2160p[4-9].*=420 .*=422", the 4K bandwidth guard stays the first rule.
      The daemon now fits the depth to the EDID: a rule names the format, and
      when the current depth is not advertised for it (the system leaves 8-bit
      after a mode switch), the nearest advertised one is used -- 4:2:2 becomes
      422,12bit, not 422,8bit which the TV does not have; a depth pinned in the
      rule itself is never overridden. An unreadable node falls back to the old
      static set. A custom rule from
      1.0.x (… .*=422) is still shown as "Custom rules: …" and is not
      overwritten.

    * No more "double jump" on a wrong player declaration: on ATV11 two
      different players declared 24 fps for a 50 Hz channel, the daemon switched
      to 24 Hz at once and the measurement 14 s later said 50, so the mode
      changed twice. The declared rate is now cross-checked against the frame
      counter (~0.7 s window): if the counter is already clearly higher
      (1.5x or more), the fast decision is not applied and the mode changes
      once, by measurement.

    * "Restore the color profile" (cs.restore, default 1): when the daemon
      returns the mode (video ended, player left the foreground) it writes back
      the format that was in effect before the switch. Otherwise a broad rule
      (.*=422) stays on the desktop too and interface text is smeared over
      chroma. The value before the first change is remembered (not the one
      present at daemon start: a previous session could have left its format).
      On ATV14 the current value is read by the vendor client
      (-g "HDMI Color ATTR"), because the attr node does not reflect what the
      client set; on the legacy path it comes from cs.path. The restore uses
      the same event as the mode return, and cs.select rules are not applied
      on that switch, so the format is not written twice.

    * An unapplied mode no longer leaves the TV without a signal: when
      SurfaceFlinger/HDMI does not take the requested mode (live case 02.11,
      tester box X5/ATV14: a 25 fps channel asked for 2160p25, the kernel stayed
      at 60 Hz and the TV showed "no signal"), the daemon confirms the mismatch
      by re-reading vinfo after 800 ms, retries the mode through the double
      rate (25 -> 50: on the tester's box 60 -> 25 did not apply while 50 -> 25
      did) and, if that fails, keeps the double rate (50 Hz for 25 fps is
      smoother than 60) or restores the original mode together with the color
      profile; no more switching until the end of the video.

    * The HDMI format is written only once the mode has settled. Previously the
      daemon wrote the color space right after the mode transaction, while the
      mode node still showed the previous mode: that write reconfigures the HDMI
      path and cancels the switch itself. The tester's log of 03.11 shows it
      directly — every 60/50 -> 25 Hz switch followed by a format write did not
      apply, and the single one without a write did; the same effect appears as
      "SurfaceFlinger mode table changed" (31 -> 37 -> 31). Now the rule is
      applied at the "mode has settled" point — 2.5 s later, after the actual
      rate is cross-checked through vinfo; if the rate is wrong, no format is
      written at all.

    * "Do not change the format" is back in the HDMI format setting. An empty
      cs.select means the daemon never writes the format — neither by a rule nor
      by a "default". 1.1.0 had no such item (every item of the list carried the
      4K protection rule), while an empty rule set in the code meant "apply the
      default", i.e. a write on every mode switch. The item is first; "Auto"
      remains the default.

    * Giving up on an unapplied mode now lasts until the end of the video: the
      measurement recheck (fps.recheck.delay.ms) no longer clears the "nothing to
      measure" flag after ~0.6 s. In the tester's log of 03.11 that produced 18
      switches in 6.5 minutes and four full cycles on a single channel; now
      there is at most one cycle per video.

    * The "auto" fractional rate policy (mode.use.fract=0) is real now on
      Android 10-14: an integer rate is used only when the source declared an
      integer one (player hint frame_rate_hint — 24.000 vs 23.976, or the
      declared frame duration frame dur — 96000/4000 vs 96000/4004); otherwise
      the fractional member stays. Before, "auto" and "fractional" were
      indistinguishable: the frame counter cannot tell the 0.1 % pair apart.
      A declared value from another rate group (garbage in the field: the
      driver reports 30 fps for real 23.976) is ignored — verified on the
      stand. The legacy path (Android 6-9) is unchanged.

    * Actual display rate is verified after a mode switch: once the mode has
      settled (2.5 s) the daemon reads sync_duration_num/den from
      /sys/class/display/vinfo and logs "фактическая частота дисплея: 23.98 Гц
      (vinfo 23976/1000)". The mode name is shared by 23.976 and 24.000, and the
      vendor SystemControl even rewrites frac_rate_policy, so only the timings
      tell what actually came out. A rate from another group than requested gets
      a separate loud line. It does not affect decisions.

    * Source cross-check. When the cadence check sees the video layer updating
      noticeably slower than the frame counter says (1.6x or more), one line with
      every number goes to the log:
        сверка источников: счётчик 59.94 Гц, подача видео-слоя 29.97 Гц
        (33 мс при периоде дисплея 20 мс), заявлено 30 fps / frame dur 3600,
        декодер amvdec_h265_fb_ status 181 — расхождение в 2.00 раза
      It answers a question that cannot be settled otherwise: is the content
      60 fps rendered by the app at 30, or does this driver's counter count
      double. Diagnostics only, it does not affect mode selection.

    * AFR on demand: a session triggered by a button (slimBOXtv request). AFR is
      normally off (enable=0); on an external command the daemon switches on for
      a while, makes ONE mode switch, restores the previous mode and switches
      off again. Inside a session the mode bump (switch.bump), the cadence
      "healing" and the measurement recheck are disabled — only the measurement
      and one switch remain; the ceiling reset stays as in the normal loop, for
      switch.bump.pkg players only. Duration: 40000 ms default, 15000..120000
      (burst.ms), repeats extend, burst 0 cancels, calls are limited to one per
      second. Four interfaces: the API command burst <ms>, the broadcast
      ru.reyter.afrd2.action.BURST, the activity ru.cobra.afrd.BURST and the
      afrd --burst <sec> utility (a running daemon first; with no daemon it runs
      a one-shot process that exits after the session). The daemon reports the
      session itself: ru.reyter.afrd2.action.BURST_STATE with state, hz_milli
      and left_ms (key burst.broadcast turns it off).

    * Less log noise: "счётчик кадров стоит" at most once per 10 s (was 42 lines
      in 8 minutes for a player that jitters the counter), "… не в
      switch.bump.pkg" at most once per minute per package (was 15 lines in
      5 minutes). Behaviour is unchanged, only the line frequency.

    * Settings: duplicate toggles removed. "Fix rate clamping" (switch.bump)
      and "Apply player correction" (fps.correct.enable) are no longer shown:
      both mechanisms have their own player list, and an empty list already
      means "off". The state "list filled in, toggle off" looked like a
      malfunction. The ini keys remain (old configs keep working), defaults
      unchanged.

    * Settings that do not apply on the current path are hidden instead of
      greyed out: on Android 10-14 the "Switch delays" group (switch.timeout
      moved to "Main"), mode.extra and the two blacklists; on Android 6-9 the
      "Android 11+ fine tuning" group and fps.correct.*. Before, they were grey
      rows with a "does not apply" note - a quarter of the screen.

    * AV1 correction is one setting instead of two keys. The additive
      (fps.correct.av1.offset) and relative (fps.correct.av1.pct) corrections
      describe the same effect and were applied together: with pct=5.7 and
      offset=0.1 a 25.000 fps clip measured 24.90, i.e. the correction worked
      twice. Now the daemon picks the model by platform: fps.correct.av1=auto
      applies the calibrated value (ATV14 - 0.1 frame/s), off disables it, and a
      number sets a percentage. In the app: "AV1 counter correction" -
      Auto / Off. The old keys are read only when the new one is absent, and
      are mutually exclusive.

    * Pause behaviour is one item "On pause" (pause.mode): keep the mode,
      keep 20 s and then restore, or restore immediately. Before it was a toggle
      "Keep the mode while paused" and a number "STOP delay" in different
      categories, although it is one choice of three states. On Android 6-9 the
      item is hidden: there switch.delay.off means something else (the delay
      before restoring the mode after the video ends).

    * The "fine tuning" group no longer shows the internal envelope constants
      (subwindow, early decision, expansion limit) or fps.measure.retries /
      fps.declared.crosscheck.pct: the UI keeps the two meaningful values - how
      long to watch and how long to warm up. The other keys still work and are
      set in the ini.

    * Restoring the mode when a video ends (switch.restore.on.stop): players
      from the "players to unclamp" list are no longer restored immediately -
      the mode is raised at the start of the next clip and restored once the
      player leaves the screen. That is one mode switch less between clips.
      The SurfaceFlinger backdoor flag is kept, otherwise the framework would
      restore the mode by its own policy.

    * Fixed mode restoration for players in the "fix rate clamping" list
      (switch.bump.pkg). After the video ended the mode was held, but nothing
      restored it when the player left the foreground: the list check was
      applied to that path too, the hold was never released, the launcher
      stayed at the video rate, and "player left the foreground - restoring"
      repeated every ~1.7 s. Live run on ATV14: 24 Hz on the launcher until the
      daemon restarted. Now the mode is restored once the player leaves the
      foreground (also with switch.restore.on.stop=0, otherwise the mode would
      stay until a daemon restart).

    * Pause restoration (pause.mode=off or a pause longer than
      switch.delay.off) is no longer blocked by the clamp list: a pause is not
      the end of a video. Before, such players never got the mode back on
      pause.


    * Fixed: the measurement could pull the mode down during live video. On a
      1080i50 channel the frame counter is throttled by the current mode and
      inflated by the player (OTT reports frame-rate=30 to the decoder), so the
      lower envelope drove 50 -> 30. The accepted rate is now a lower bound, but
      only when it is a multiple of the declared one (2x/3x, 4 % tolerance):
      50 vs 25 — yes, 25 vs 24 — no. A decoder micro-restart (OTT recreates it
      every 20-50 s) does not reset the bound: 90 s at 50 Hz with no switches.

    * A short settle down from the maximum after the bump
      (switch.bump.probe.ms, 2500 ms, 0 — off): the envelope decision used to
      wait 14-31 s and the screen stayed at the maximum all that time; now the
      mode is chosen from the video layer data after 2.5 s (and every second
      after that). Live measurement: the maximum is held ~5.3 s instead of
      14-31 s.

    * Fixed: switch.skip.pkg did not actually block mode changes on the new
      path since 1.0.0 — the gate was applied after the fast decision, so a
      player listed under "AFR interferes" still got switched. Now neither the
      measurement, nor the fast decision, nor the recheck, nor the reapply runs
      for such a player.

1.1.0 Tue Oct 27 2026

    Release after the 1.0.0 publication: the main thing is that frame rate
    "clamping" on Android 11+ is fixed and mode switching on Android 10/11 is
    faster. The claim is unchanged (Android 11-14, Amlogic); the legacy path
    (Android 6-9) is untouched.

    * Rate clamping. A player (measured on the stock YouTube TV) remembers the display
      rate at the start of a playback session and does not re-read it when the
      mode changes externally: a video started at 50 Hz kept delivering ~50 fps
      after the switch to 60 Hz, and the picture stayed juddery until playback
      was restarted (layer presentation: 49.4 vs 59.94 fps). The daemon now:
        - raises the mode to the TV maximum before the player's first frame
          (switch.bump), including right when the decoder channel disappears on a
          roll change and when a player comes to the foreground
          (switch.bump.on.app) - this also covers cold starts, where the decoder
          appears later than the player fixes its rate;
        - if the switch still landed on a live video, resets the player's rate
          ceiling (switch.ceiling.reset): by restarting the codec process, and
          by bumping the display density if that fails. The player re-reads the
          mode and delivery recovers from the current playback position.
      Live measurements: ATV14 - 50.34 -> 59.94 fps, an 83 ms delivery gap;
      Android 11 - 49.4 -> 59.9 fps by the 8th second.

    * A persistent mode-switch helper on Android 10/11 (vendor.disp.persist).
      Previously every switch started a separate app_process (~490 ms out of
      0.85-1.76 s). The helper keeps the VM and HIDL classes loaded: a switch
      takes 0.34-1.09 s (measured on two TVs). Any failure falls back to the
      one-shot launch, so the key can be disabled safely.

    * The stock YouTube app is no longer excluded from frame rate matching on
      any path (Android 11-14): clamping is fixed, so it is handled like any
      other player. On Android 10/11 the former exclusion was based on a
      "reset costs 1.5-2.5 s" estimate that a live measurement did not
      confirm (the real figure is 0.26 s). An installed app migrates the
      setting on update (only the stock YouTube package is removed, the
      user's own entries are kept).

    * The clamping mechanisms apply only to the players in switch.bump.pkg
      (stock YouTube by default). Clamping was measured there; for other
      players it is not confirmed, and the fallback ceiling reset is a display
      configuration change that restarts the Activity in some players
      (OTT Navigator returned to the previous channel on the first AFR switch).
      An empty list disables the mechanisms completely and leaves plain
      measurement. A player listed under "Players that AFR disturbs"
      (switch.skip.pkg) never gets the mechanisms: that list promises to leave
      the mode alone. The app has a new "Players to fix clamping for" item.

    * Defaults for the clamping mechanics on Android 11-14 now follow the
      verified scheme. `switch.skip.pkg` is empty on every path: the stock
      YouTube is no longer excluded (on 10/11 it was there because of a
      "reset costs 1.5-2.5 s" estimate that did not hold — the real figure is
      0.26 s). `switch.ceiling.reset` is on by default on both paths: its
      default follows `switch.bump`, but the reset itself does not depend on
      the bump and, with the bump off, remains the only protection against
      clamping. The default method is a codec restart
      (`switch.ceiling.method=auto`):
      it does not change the display mode, so clamping is fixed without an
      extra mode switch and the playback position is preserved. Measured on
      Android 11: 50.02 -> 59.94 fps in 0.26 s.

    * Ceiling reset by restarting the codec (switch.ceiling.method). The old
      way - a display density change - relaunches the Activity and costs 6.8 s
      of "waiting"; the new one recreates only the decoder session, and the
      player continues from the current position: measured on ATV14, the
      decoder disappears for 68 ms and is back in 1.1 s. The service name is
      discovered via init (Codec2 on Android 12+, OMX on 8-11), so the method
      also suits Android 10/11 where the density change cost 1.5-2.5 s.
      Default `auto`: codec restart, density change as a fallback; `density`
      restores the previous behaviour. The reset is done once per video,
      deferred, and only when the target mode is above the mode the video
      started under. Cost: the HAL is restarted, i.e. the
      decoder of every application at once (background playback in another
      app will be interrupted).

    * Rate readings on Android 10/11 now match the actual rate. A mode name
      covers both variants (`1080p60hz` is both 60.000 and 59.940), the
      fractional policy comes from the frac_rate_policy node, and the TV mode
      list holds nominal values only: the daemon showed 60.00 Hz while the
      display ran at 59.940061 (in the app, in `afrd -s` and in the
      notification), and that was taken for the daemon switching the "base
      frequency". The report now honours the display policy: 59.94 at
      frac_rate_policy=1 and 60.00 at 0.

    * The fractional rate on Android 10/11 follows the content. There a mode
      name covers both 24.000 and 23.976 and the actual rate comes from the
      frac_rate_policy node; the daemon never wrote it, so on a box with policy
      0 a 23.976 film played at 24.000 (one repeated or dropped frame every
      ~41 s). The policy is now written before the mode is applied - the same
      way the stock DroidLogic AFR does it - and restored afterwards so the
      desktop stays at 60.000. The mode.use.fract key applies here too: 2 is
      the integer member, 0/1 the fractional one.

    * Relative AV1 counter correction (fps.correct.av1.pct): the overcount is
      proportional to the rate (23.976 -> 25.40, 59.94 -> 63.30) and the previous
      additive correction could not fix it. Off by default.

    * The app finds a working su on stock firmware. On Amlogic userdebug builds
      the old AOSP su comes first in PATH and does not understand `-c`, while
      Magisk keeps its su in /debug_ramdisk/su: the app reported "root required"
      although root was present. Candidates are now probed and only one returning
      uid=0 is accepted.

    * "Blacklisted refresh rates" (mode.blacklist.rates) are picked from the
      rates the TV supports instead of typed as numbers: 23.976 and 24 are
      different entries, and guessing the right one from a hint was impossible.
      The list also contains fractional variants (23.976, 29.97, 59.94): on the
      legacy path a mode name covers both variants, so a blacklist of "24" did
      not filter out 23.976.

    * "HDMI format (color space)" (cs.select) is a choice of three items instead
      of a line with regular expressions; the 4K bandwidth rule is kept in each.

    * "Fix frame rate clamping" - one switch for both clamping mechanisms. Both
      mechanisms (raising the mode and resetting the rate ceiling) apply only to
      the players listed in "Players to fix clamping for" (switch.bump.pkg, the
      stock YouTube by default): for players with their own matching a codec
      restart breaks playback - on OTT Navigator this shows as errors and a
      frozen picture when switching channels.

    * The delivery check now measures the video layer of the app that owns the
      decoder instead of the first SurfaceView in the list: a foreign layer
      (wallpaper, overlay, a leftover from a previous player) produced a bogus
      rate and an extra mode switch. The expectation for that check comes from
      the same rate the mode was chosen for, and the back-and-forth "heal" is
      not repeated when the first attempt did not change delivery: the cause is
      then not the display, and a repeat only blinks the screen.

    * The daemon re-reads the current display mode before deciding on a switch:
      it used to trust its cache, while the mode could be changed by someone else
      (the built-in Amlogic AFR, a player with its own matching), and a 60 fps
      video stayed at 25 Hz.

    * The end-of-video wait no longer slows IPTV channel zapping down. The stop
      debounce ("Stop debounce, ms") is now interrupted as soon as the decoder
      reappears: previously the daemon was blind for the whole window, and with
      10000-12000 (the recommendation for IPTV whose channel takes 5-10 s to
      open) the rate on a new channel lagged by the whole window - a live
      measurement showed 24 Hz arriving after 26 s instead of 14. The same
      change cures blinking while zapping: a dead channel no longer restores
      60 Hz, and the next live channel sets its own rate.

    * The post-switch delivery check no longer fires falsely after a pause.
      Frame intervals are taken by median, not by mean: the SurfaceFlinger
      buffer still holds frames shown before the pause, and a single 28 s gap
      made the mean 272 ms against the real 42 ms, so the daemon switched the
      mode back and forth right on resume (live finding 29.10 on ATV14, §89).

    * Fixed an app crash when launched on a sleeping box (Android 8-9): the root
      check ran in a background task and the system refused the service start;
      the service now starts via startForegroundService, a refusal no longer
      crashes the app, and the start is retried when the window gains focus.

    * Log: "HDMI not active" is printed only on a real HDMI event, not on an
      intentional config reload.

    * Documentation: how to calibrate the rate correction
      (tools/stand/fps_calib.sh), unknown box recon (tools/stand/recon_box.sh),
      TV switch latency measurement (tools/stand/tv_switch_lat.sh), and a guide
      for ROM integration.

1.0.0 Thu Oct 08 2026

    First public build of the fork. Below are the differences from AFRd 0.3.2;
    later versions get ordinary change entries.

    Android 11 (Amlogic, kernel 5.x) — the vendor mode-switching path (11 is
    the claimed version; Android 10 ships kernel 4.9 and therefore uses the
    legacy path, but there is no live verification on 10):

    * The mode is switched by the vendor SystemControl HAL (HIDL
      vendor.amlogic.hardware.systemcontrol, setActiveDispMode) — the same
      mechanism the built-in system AFR uses. The SurfaceFlinger transaction
      path does not work on these versions, and on Android 11 calling it with a
      single argument crashes SurfaceFlinger. The vendor APK with the HIDL proxy
      classes is looked up across /system_ext, /system, /vendor and /product,
      and the interface version is tried from V1_1 down to V1_0 — the
      /system_ext partition exists only since Android 11.
    * The mode is chosen by NAME from disp_cap (there is no SurfaceFlinger mode
      table here); the helper (app_process + dex) ships in the APK and in the
      Magisk module.
    * Fast decision by the declared frame rate is enabled by default: the mode is
      applied immediately from the vdec_status "frame rate" field (the way the
      system AFR does it — hence its speed), but the decision is verified by our
      own measurement and corrected on mismatch. Key: fps.declare.fast.
    * Without the vendor service or the helper the daemon falls back to the
      passive mode with a warning — modes are untouched, API and stats work.

    Fixes in this code path (found by an independent review and a live run before
    publication):

    * The mode-switching helper looks for its dex next to its own script rather
      than in /data/local/tmp: on a clean install switching did not work at all.
    * The app re-extracts the helper if the files are gone or truncated (the
      system clears the cache when space runs out); previously switching died
      silently until the next app update.
    * A hung helper (e.g. stuck inside a vendor service call) no longer stalls
      the daemon: external commands have an anti-hang deadline (10 s, not
      configurable through a key) and their whole process tree is taken down.
    * A helper failure is not retried on every loop iteration: one attempt per
      video instead of dozens of log lines and process launches mid-movie.
    * The fast decision by the declared frame rate remembers the original mode,
      so restoration on stop works in the honest case too (previously the home
      screen stayed at the video's rate).
    * The default of the "Fast decision by declared frame rate" setting no longer
      enables that path on Android 12-14: the value depends on the OS version.
    * The daemon watchdog now works on the legacy path (Android 6-9) too: after a
      crash (kill -9, kernel panic) the app restarts it and it returns the held
      mode. Previously the heartbeat check existed only on the new path, and the
      heartbeat itself was updated only in the new loop: on Android 6-9 the
      daemon was not restarted, the mode stayed foreign until a reboot, and the
      GUI reported "daemon enabled" from the dead process's status (live finding
      2026-10-09).
    * `afrd -s`, the API and the app on the vendor path (Android 10/11) report real
      refresh rates
      (used to be 0 Hz and "mode not switched"), and they do so right after
      changing the settings: previously, for a few seconds after a config reload
      they showed "daemon disabled" and 0 Hz — until the daemon finished its
      platform probe (live finding of the 2026-10-09 acceptance run).
    * A config reload (editing `afrd.ini` or changing the app settings) no longer
      leaves the daemon holding addresses of freed strings from the previous
      config: the TV mode list was read from such an address, and the log got a
      parse of an unrelated file instead of the mode list (live finding of the
      2026-10-09 acceptance run: first the mode-switch helper, then the colour
      space list).
    * The `vendor.disp.cap` key works again (the TV mode list is read from it);
      an unreadable list produces a single warning and the mode is left alone.

    Android 12-14 (kernel 5.x) — the new code path:

    * The HDMI mode is switched by the stock SurfaceFlinger mechanism, so it stays
      in sync with the system: video and UI never disagree. On firmware without
      that mechanism (including Android 10 and 11, where the service call is taken
      by a different operation) the daemon says so in the log and leaves the
      system alone.

    * The frame rate is measured from the decoder frame counter using the lower
      envelope of observation sub-windows rather than a single window, so short
      spikes and repeated frames do not spoil the decision. If the player reports
      the rate itself (frame_rate_hint), its value wins.

    * Mode behaviour is configurable: on pause the mode is held by default, on
      video stop the original mode is restored (both are switchable). Pause
      patience is set separately (switch.delay.off): by default the mode is held
      until the pause ends; with a non-zero value a long pause counts as the end
      of the video, the original mode is restored, and on resume the held mode
      comes back without a new measurement. This is the only way to tell a pause
      from a stopped video with the player still on screen: the system does not
      distinguish them.

    * The daemon verifies that frames actually reach the screen and fixes
      "half-rate" output; it also logs the case where the player itself sets the
      pace (AFR gets in the way of such a player — see below).

    * Player exit and a stuck decoder channel are detected: the mode is not left
      behind when the video ends or the app leaves the screen.

    * Colour space rules (cs.select) apply here too, through the vendor service.
      HDR/SDR attributes are read and shown but never changed: the system and the
      player own them.

    * The app watches the daemon and restarts it if it stops. If the daemon died
      while holding a mode (crash, force stop), the restarted daemon restores the
      original mode: otherwise the launcher would stay in a low refresh rate until
      reboot — SurfaceFlinger does not reset the mode itself, and the service flag
      is cleared by the system within seconds.

    Android 6-9 — the previous AFRd behaviour; shared settings were ported:

    * "Players AFR gets in the way of" (switch.skip.pkg): for the selected players
      the daemon measures the rate and logs everything but does not switch the
      mode. Such players fix their render pace at clip start, and a mode held from
      the previous clip throttles the next one — which broke clip browsing. The
      stock YouTube is in the list by default.

    * "Minimum mode rate for players" (mode.min.hz.list): modes below the given
      rate are not chosen for those players.

    App:

    * Name AFRd2, package ru.reyter.afrd2.

    * Players are picked from the list of installed apps — the package name is no
      longer typed with the remote; per-player rate corrections are set there too.

    * Settings that do not apply on the current Android version are marked in the
      app, and the daemon names them in the log at startup.

    * The configuration is re-read without stopping the daemon (reconf), so
      settings apply without a restart.

    Installation: the application (APK) or a Magisk module to run without the app
    (it has no interface — settings are edited in a file). Only one of the two at
    a time.

    Known limitations (by design) — see README: the daemon changes the frame rate
    only, never resolution or HDCP, does not manage HDR, and does not blank the
    screen while switching.
