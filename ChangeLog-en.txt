1.0.1 Thu Oct 15 2026

    * "Blacklisted refresh rates" (mode.blacklist.rates) are now picked from the
      rates your TV supports instead of typed as numbers: the daemon compares the
      blacklisted rate with the mode rate numerically, so 23.976 and 24 are
      different entries and guessing the right one from a hint was impossible.
      The list is built from the TV modes (disp_cap) and the SurfaceFlinger mode
      table; rates already present in the setting but absent on this TV are shown
      and not lost. The list also contains fractional variants of the rates found
      in mode names (23.976, 29.97, 59.94): on the legacy path a mode name covers
      both variants ("1080p24hz" is either 24.000 or 23.976, the fraction is set
      by frac_rate_policy), while the setting entries are different - without the
      fractional variant a blacklist of "24" did not filter out the 23.976 mode
      (live acceptance 2026-10-15, Android 9 stand).

    * "HDMI format (color space)" (cs.select) is now a choice of three items
      instead of a line with regular expressions: "Auto (4:2:0 on 4K only)",
      "RGB instead of YUV", "YUV 4:4:4". The 4K bandwidth rule is kept in every
      item (at 4K 50/60 Hz neither 4:4:4 nor RGB fits the HDMI link). A custom
      value left over from older versions is shown as a separate item and is not
      overwritten.

    * The daemon re-reads the current display mode before deciding on a switch.
      It used to trust its own cache, while the mode could be changed by someone
      else (the built-in Amlogic AFR, a player with its own frame rate matching,
      a manual sysfs write): the mode-change uevent on kernel 4.9
      (vout/extcon/setmode) is unknown to the daemon. The result was visible to
      the eye - a 60 fps clip stayed at 25 Hz because the daemon believed the
      current mode was 60 Hz and wrote "Skipping mode switch since current
      refresh is close enough" to the log (live measurement 2026-10-15, ATV9
      stand). The decision now also accounts for the current resolution: after an
      external resolution change the mode used to be picked for the previous one.

    * FAQ: two new questions. "Can the mode be switched faster than in 10-20
      seconds?" - about the fast decision by the declared frame rate (this
      question did not make it into the published 1.0.0 build). "Should I choose
      the APK or the Magisk module?" - the difference in the wrapper and the
      scenarios where the module is preferable. The answers about green-ish
      image / black screens and about blacklisted refresh rates are rewritten for
      the two new picker items instead of text fields.

    * README: a "Integration into firmware" section; a "What to choose" paragraph
      (APK, Magisk module, a daemon built into the firmware - and why two of them
      must not be kept at the same time); descriptions of the two new picker
      items.

    * The bundle now includes docs/integration-rom.md - for the case when the
      daemon is built into a firmware (minimal setting set, different keys for
      Android 9 and 11-14, firmware requirements, API, acceptance steps). The
      document is not part of the build.

    * Fixed the app crash on launch on a sleeping box (Android 8-9). The root
      check ran in a background task and the service start was called from it:
      while `su` waited for the Magisk dialog, the system came to treat the app
      as background and answered "Background start not allowed". The exception
      was not caught, so the app died with FATAL EXCEPTION. Now the check result
      is delivered to the main thread, the service is started via
      startForegroundService (the same way as on boot), a system refusal no
      longer crashes the app, and the start is retried once the window gets
      focus (a sleeping box has none).

    * Log: "HDMI not active, clearing video mode list" is printed only on a real
      HDMI event. It used to be printed on the deliberate mode-list release
      during a config reload as well, and next to "config file ... changed,
      reloading" it read as an HDMI failure (a non-existent fault was already
      investigated because of it). The release now lives in a separate function;
      a redundant HDCP state reset on re-init is gone too.

1.0.0 Thu Oct 08 2026

    First public build of the fork. Below are the differences from AFRd 0.3.2;
    later versions get ordinary change entries.

    Android 11 (Amlogic, kernel 5.x) — the vendor mode-switching path (11 is
    the claimed version; Android 10 ships kernel 4.9 and therefore uses the
    legacy path, but there is no live verification on 10):

    * The mode is switched by the vendor SystemControl HAL (HIDL
      vendor.amlogic.hardware.systemcontrol, setActiveDispMode) — the same
      mechanism the built-in system AFR uses. The SurfaceFlinger transaction
      path does not work on these versions, and on Android 11 calling it with a
      single argument crashes SurfaceFlinger. The vendor APK with the HIDL proxy
      classes is looked up across /system_ext, /system, /vendor and /product,
      and the interface version is tried from V1_1 down to V1_0 — the
      /system_ext partition exists only since Android 11.
    * The mode is chosen by NAME from disp_cap (there is no SurfaceFlinger mode
      table here); the helper (app_process + dex) ships in the APK and in the
      Magisk module.
    * Fast decision by the declared frame rate is enabled by default: the mode is
      applied immediately from the vdec_status "frame rate" field (the way the
      system AFR does it — hence its speed), but the decision is verified by our
      own measurement and corrected on mismatch. Key: fps.declare.fast.
    * Without the vendor service or the helper the daemon falls back to the
      passive mode with a warning — modes are untouched, API and stats work.

    Fixes in this code path (found by an independent review and a live run before
    publication):

    * The mode-switching helper looks for its dex next to its own script rather
      than in /data/local/tmp: on a clean install switching did not work at all.
    * The app re-extracts the helper if the files are gone or truncated (the
      system clears the cache when space runs out); previously switching died
      silently until the next app update.
    * A hung helper (e.g. stuck inside a vendor service call) no longer stalls
      the daemon: external commands have an anti-hang deadline (10 s, not
      configurable through a key) and their whole process tree is taken down.
    * A helper failure is not retried on every loop iteration: one attempt per
      video instead of dozens of log lines and process launches mid-movie.
    * The fast decision by the declared frame rate remembers the original mode,
      so restoration on stop works in the honest case too (previously the home
      screen stayed at the video's rate).
    * The default of the "Fast decision by declared frame rate" setting no longer
      enables that path on Android 12-14: the value depends on the OS version.
    * The daemon watchdog now works on the legacy path (Android 6-9) too: after a
      crash (kill -9, kernel panic) the app restarts it and it returns the held
      mode. Previously the heartbeat check existed only on the new path, and the
      heartbeat itself was updated only in the new loop: on Android 6-9 the
      daemon was not restarted, the mode stayed foreign until a reboot, and the
      GUI reported "daemon enabled" from the dead process's status (live finding
      2026-10-09).
    * `afrd -s`, the API and the app on the vendor path (Android 10/11) report real
      refresh rates
      (used to be 0 Hz and "mode not switched"), and they do so right after
      changing the settings: previously, for a few seconds after a config reload
      they showed "daemon disabled" and 0 Hz — until the daemon finished its
      platform probe (live finding of the 2026-10-09 acceptance run).
    * A config reload (editing `afrd.ini` or changing the app settings) no longer
      leaves the daemon holding addresses of freed strings from the previous
      config: the TV mode list was read from such an address, and the log got a
      parse of an unrelated file instead of the mode list (live finding of the
      2026-10-09 acceptance run: first the mode-switch helper, then the colour
      space list).
    * The `vendor.disp.cap` key works again (the TV mode list is read from it);
      an unreadable list produces a single warning and the mode is left alone.

    Android 12-14 (kernel 5.x) — the new code path:

    * The HDMI mode is switched by the stock SurfaceFlinger mechanism, so it stays
      in sync with the system: video and UI never disagree. On firmware without
      that mechanism (including Android 10 and 11, where the service call is taken
      by a different operation) the daemon says so in the log and leaves the
      system alone.

    * The frame rate is measured from the decoder frame counter using the lower
      envelope of observation sub-windows rather than a single window, so short
      spikes and repeated frames do not spoil the decision. If the player reports
      the rate itself (frame_rate_hint), its value wins.

    * Mode behaviour is configurable: on pause the mode is held by default, on
      video stop the original mode is restored (both are switchable). Pause
      patience is set separately (switch.delay.off): by default the mode is held
      until the pause ends; with a non-zero value a long pause counts as the end
      of the video, the original mode is restored, and on resume the held mode
      comes back without a new measurement. This is the only way to tell a pause
      from a stopped video with the player still on screen: the system does not
      distinguish them.

    * The daemon verifies that frames actually reach the screen and fixes
      "half-rate" output; it also logs the case where the player itself sets the
      pace (AFR gets in the way of such a player — see below).

    * Player exit and a stuck decoder channel are detected: the mode is not left
      behind when the video ends or the app leaves the screen.

    * Colour space rules (cs.select) apply here too, through the vendor service.
      HDR/SDR attributes are read and shown but never changed: the system and the
      player own them.

    * The app watches the daemon and restarts it if it stops. If the daemon died
      while holding a mode (crash, force stop), the restarted daemon restores the
      original mode: otherwise the launcher would stay in a low refresh rate until
      reboot — SurfaceFlinger does not reset the mode itself, and the service flag
      is cleared by the system within seconds.

    Android 6-9 — the previous AFRd behaviour; shared settings were ported:

    * "Players AFR gets in the way of" (switch.skip.pkg): for the selected players
      the daemon measures the rate and logs everything but does not switch the
      mode. Such players fix their render pace at clip start, and a mode held from
      the previous clip throttles the next one — which broke clip browsing. The
      stock YouTube is in the list by default.

    * "Minimum mode rate for players" (mode.min.hz.list): modes below the given
      rate are not chosen for those players.

    App:

    * Name AFRd2, package ru.reyter.afrd2.

    * Players are picked from the list of installed apps — the package name is no
      longer typed with the remote; per-player rate corrections are set there too.

    * Settings that do not apply on the current Android version are marked in the
      app, and the daemon names them in the log at startup.

    * The configuration is re-read without stopping the daemon (reconf), so
      settings apply without a restart.

    Installation: the application (APK) or a Magisk module to run without the app
    (it has no interface — settings are edited in a file). Only one of the two at
    a time.

    Known limitations (by design) — see README: the daemon changes the frame rate
    only, never resolution or HDCP, does not manage HDR, and does not blank the
    screen while switching.
