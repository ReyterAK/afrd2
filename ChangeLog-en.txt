0.3.3 Fri Oct 02 20:05:00 MSK 2026

    The AV1 correction is enabled with the value 0.1 — the largest one at which no
    25 fps clip is pushed into 24 Hz. Tuned on live recordings (13 YouTube clips,
    the same statistic the daemon uses — lower envelope): without the correction
    "24 correct / 25 correct" = 5/7 and 6/6; at 0.1 — 6/7 and 6/6; at 0.3 — 6/7
    and 5/6 (a genuine 25 fps clip lands in 24 Hz); at 0.5 — 7/7 and 4/6. In the
    application: "Apply player calibration" is on, "AV1 correction" = 0.1.

    No value gives a "100 %" guarantee: on a 65-clip control sample two genuine
    25 fps clips measured below the class boundary with no correction at all (the
    envelope is biased downwards), and the spread within a single playback reaches
    ±0.5 frames/s.

0.3.3 Fri Oct 02 19:45:00 MSK 2026

    The AV1 correction (fps.correct.*) is now off by default. The owner compared on
    a TV (all picture "enhancers" disabled): 24 fps video in a 25 Hz mode looks
    noticeably better than 25 fps in a 24 Hz mode. The correction moves the
    measurement downwards, i.e. can produce exactly the worse side, while its gain
    is small and does not reproduce from run to run. The keys remain — enable them
    deliberately, for a specific player or decoder path.

    Application settings now take effect immediately: after the config is written
    the daemon is woken up, so the "enable automatic frame rate matching" switch
    (and the notification "AFR on/off" action) apply within ~5 seconds, without
    restarting the daemon. Previously turning it off had no effect until the daemon
    was restarted.

0.3.3 Fri Oct 02 19:00:00 MSK 2026

    Display attributes (HDR Mode, HDR Policy, HDR Priority, SDR Mode, FORCE HDR
    Mode) are read from the built-in service and shown in the log (with -v) and
    in the API status reply. The daemon only reads them: HDR/SDR modes are still
    chosen by the system and the player.

    A memory leak on config reload is fixed: the pointer array of the string
    lists (decoder blacklists) was not freed.

0.3.3 Fri Oct 02 18:20:00 MSK 2026

    Fixed a daemon crash on config reload (the reconf command or editing
    afrd.ini): the freed pointer to the current color space was not cleared, so
    the next initialization freed the same memory again (double free, heap
    corruption). It took two reloads in a row — reproduced live on ATV14. The
    file-change check on the legacy path now uses the shared function (one rule
    instead of two copies).

0.3.3 Fri Oct 02 18:10:00 MSK 2026

    Config reload (the reconf API command or editing afrd.ini) now works on
    Android 10-14 too. Previously the new path read the keys once on entry, and
    the daemon had to be restarted after editing the file.

    The daemon notices the file change and the reconf command, restores the
    original mode, releases the mode-switch flag, re-reads the config and keeps
    running — without restarting the process and without interrupting the API.

0.3.3 Fri Oct 02 18:00:00 MSK 2026

    The daemon no longer gets stuck on decoder leftovers and can detect the rate
    when the frame counter is silent; color space settings are applied on
    Android 10-14 again.

    If the player is closed but a decoder instance remains (the frame counter
    stands still), the daemon notices that the application has left the
    foreground and releases the mode hold — previously the mode stayed with the
    mode-switch flag set until a reboot.

    When the decoder frame counter is silent but the picture is running, the rate
    is taken from video layer submission — a source that does not depend on the
    counter.

    The color space (cs.select rules) is applied on Android 10-14 as well: the
    value is set through the built-in service after a mode switch.

0.3.3 Fri Oct 02 12:00:00 MSK 2026

    The application and the daemon are now called AFRd2.

    Previously the mode was switched only after twenty seconds of observation. Now,
    when two independent rate measurements agree, the switch happens earlier.

    After switching, the daemon checks that frames really reach the display and, on
    a "half rate" picture (video looks like thirteen frames per second), switches
    the mode once more.

    If the daemon stops working, the application starts it again; the stuck
    mode-switch flag is released, and applications with their own frame rate
    matching can change the mode again.

    The active decoder channel is chosen by the growing frame counter, so a stuck
    channel no longer prevents rate detection.

0.3.2 Tue Sep 29 2026

    AFRd was forked: support for Android 10-14 added, the old path (Android 6-9)
    is unchanged.

    On newer kernels the decoder does not report video start and stop, so the
    daemon polls the decoder state itself and switches the mode through the stock
    SurfaceFlinger mechanism.

    The rate is detected from the decoder frame counter (lower envelope over
    sub-windows), with a correction for AV1.
